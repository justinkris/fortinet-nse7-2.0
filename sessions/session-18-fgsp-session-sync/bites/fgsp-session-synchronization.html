STUDY BITE · 5–10 MIN · SESSION 18

FGSP — Session Synchronization

Fast recall pass. If any of this doesn't click immediately, revisit the Complete Study Guide.

OVERVIEW

FGSP lets two (or more) independently managed FortiGates survive each other's failures by sharing only the session table — no shared identity, no shared config, no elected primary. It's the answer whenever an external load balancer owns traffic distribution and failure detection, and the firewalls behind it can't or won't merge into a single FGCP identity.

PROBLEM IT SOLVES

FGCP demands two things: an internally-elected decision-maker for session ownership, and full config/identity coupling. Colo deployments, multi-team environments, and anything sitting behind an existing external LB routinely violate both. FGSP removes the requirement entirely — the two boxes stay fully independent and share nothing except live session state.

PRIMARY MENTAL MODEL
Remember this first
No vMAC. No election. No config sync. The only thing crossing between FGSP peers is a copy of the session table — and even that only gets acted on when a specific packet actually lands on the wrong box.
SIMPLIFIED PACKET FLOW — ASYMMETRIC HANDBACK
  1. FGT-1 receives the first packet of a session → FGT-1 becomes the session owner.
  2. Session entry syncs to FGT-2 (TCP/IPsec: automatic; UDP/ICMP/expectation/NAT: opt-in).
  3. LB routes a later packet in the same session to FGT-2 instead.
  4. FGT-2 doesn't process it independently — it hands it back to FGT-1:
    • Same subnet, L2 adjacent (layer2-connection available) → direct frame bounce to FGT-1's MAC.
    • No L2 adjacency (default, e.g. cloud) → UDP-encapsulated over Layer 3 to FGT-1's IP.
  5. FGT-1 processes the packet normally. Only that one packet paid a cost — everything else flows straight through.
KEY TERMINOLOGY
TermMeaning

session-pickup-natOpt-in sync for NAT'd sessions

session-sync-devOptional dedicated interface for L2 session sync (auto-fallback to L3)
standalone-cluster encryptionIPsec-encrypts the L3 sync channel (psksecret)
EXAM-CRITICAL POINTS
Trap: "Active-Active" is not the signal for FGSP. FGCP does Active-Active too. The real marker is no shared identity/config plus an external device making the routing decision.
Default sync: TCP + IPsec sync automatically. UDP/ICMP/expectation/NAT are opt-in.
IPsec nuance: a synced SA is a failover benefit (owner dies → peer takes over, no renegotiation) — NOT a live-processing shortcut. While the owner is healthy, a misrouted IPsec packet still gets handed back like everything else.
COMMON MISTAKES
  • Assuming FGSP peers need to be L2-adjacent — they don't, for session sync alone (Layer 3 is the default). L2 adjacency only matters for the config-sync feature and for choosing the L2 handback mechanism.
  • Treating a lagging sync channel like FGCP split-brain. FGSP has no identity to contest — lag just means a stray packet gets dropped and TCP retransmits. Self-healing, not a crisis.
  • Assuming a synced IPsec SA lets any peer decrypt mid-flow traffic freely. It doesn't — the uniform handback mechanism still applies while the owner is alive.
TROUBLESHOOTING CHECKLIST
  • Confirm which peer is the session owner (received the first packet) before assuming a "failure."
  • Check layer2-connection setting — mismatched L2 assumptions between peers cause handback failures.
  • Verify the LB's return-path routing behavior — is asymmetry occasional (expected) or constant (design problem)?
  • For UDP-heavy or NAT-heavy traffic behaving oddly after failover, check whether the relevant session-pickup-* flag is actually enabled.
  • For cross-datacenter sync links, confirm encryption is enabled if the path crosses shared infrastructure.
MEMORABLE ANALOGY
Two Roommates, One Notebook
Separate bank accounts, separate leases, separate house rules — but one shared notebook by the door: "let this person in, they're fine to use either door going out too." Neither roommate needs the other's permission to act on what's written — they just need the notebook to be current. When it lags by a few seconds, worst case someone waits at the door a moment. Nobody's fighting over whose house it is.
SELF-TEST
  1. Why does FGCP's config sync make "the colo team manages their own box" structurally impossible, independent of any traffic consideration?
  2. Out of 1000 packets with only 1 misrouted, how many pay a relay cost under FGSP vs. under FGCP Active-Active — and why is that number so different?
  3. What's the difference between the L2 and L3 asymmetric handback mechanisms, and which one is the default?
  4. Why does Fortinet sync TCP and IPsec by default but leave UDP/ICMP opt-in?
  5. Why doesn't a lagging FGSP sync channel cause split-brain the way a dropped FGCP heartbeat can?
