CONCEPTS LEARNED
================

1. diagnose sys session list — Why This Command
Lives under diagnose, not get. get produces operational summaries for administrators. diagnose exposes raw internal engine state. When you need proof that a specific session is hitting the NP7, you need engine state — not a summary. The session table lives here precisely because it shows what the forwarding engine is actually doing.

2. Anatomy of a Session Entry
The npu info line is the verdict line. Everything else — proto, duration, src, dst, state flags — provides context about the session but says nothing about where processing is happening. The exam will show full session entries. Go straight to npu info.

3. Decoding offload=X/Y
X = forward direction (source to destination). Y = reverse direction (destination to source). The number is an internal processor code, not a packet count.
  9 = NP7 (fast path — CPU bypassed after session setup)
  0 = CPU (slow path — full software processing)
offload=9/9 = both directions on NP7 = fully offloaded = Priya's proof.
offload=0/0 = both directions on CPU = investigate via no_ofld_reason.

4. The Constraint vs Decision Framework
This is the session's most important concept.

ARCHITECTURAL CONSTRAINTS — cannot be configured away:
  - Session Helpers: Protocols like FTP and SIP negotiate secondary connection ports inside application payloads. FortiOS session helpers (CPU software) watch this negotiation and dynamically open pinholes. The NP7 is a forwarding engine, not a payload parser — it cannot do this. Any session requiring a helper stays on the CPU for its entire lifetime. no_ofld_reason: helper.
  - Software Tunnel Interfaces: GRE tunnels and SSL VPN tunnels run in software on the CPU. The tunnel processing itself lives on the CPU — so any session flowing through a software tunnel interface is CPU-bound regardless of policy. IPsec is the exception: the NP7 has dedicated crypto engines. no_ofld_reason: software-tunnel.
  - Very Short-Lived Sessions: The NP7 takes over after the first packet — the CPU processes packet one, installs the session key, then steps aside. For sessions that complete in one or two packets (DNS queries, ICMP), the session is already finished before the NP7 ever forwards anything. Not a problem — mathematics.

CONFIGURATION DECISIONS — can be reversed:
  - Proxy-Based UTM Profile: Any proxy-mode profile attached to a policy forces all matching sessions to the CPU slow path. All of them. no_ofld_reason: disabled-by-profile.
  - Explicit Policy Override: A firewall policy with set auto-asic-offload disable forces CPU processing. Classic forgotten troubleshooting override. no_ofld_reason: disabled-by-policy.

5. The Troubleshooting Methodology
Step 1: Read no_ofld_reason in the session entry you already have. It classifies the cause before you touch any other command.
Step 2: Constraint (helper / software-tunnel)? Stop. Expected behaviour. Move on.
Step 3: Decision (disabled-by-profile / disabled-by-policy)? Find the matching policy and correct it.

The session entry you already have is the first diagnostic tool. Read the evidence before reaching for another command.

TROUBLESHOOTING EXPERIENCE
==========================

Fault Scenario: Vaultline Financial — junior engineer reports offload=0/0 on trading VLAN sessions.

Troubleshooting Process Developed:
1. Read no_ofld_reason before opening any other command — it categorises the cause immediately
2. Constraint → stop. Decision → continue.
3. disabled-by-profile: find policy, check proxy profile, determine if intentional
4. disabled-by-policy: find policy, find set auto-asic-offload disable, re-enable
5. After fix: clear sessions, verify offload=9/9

Key Lessons:
- The session entry already contains the first answer. Read before reaching.
- no_ofld_reason: helper is not a problem. Treating it as one is wasted effort and an exam trap.
- disabled-by-profile and disabled-by-policy look similar but have different root causes and different fixes.
