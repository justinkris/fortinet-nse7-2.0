💭 THINK FIRST · SESSION LIST

Priya wants proof — not a general explanation — that trading sessions are hitting the NPU. You have a CLI tool that exposes raw internal engine state. What would you show her, and what specifically would you look for?

  • Why is diagnose sys session list the right command rather than a get command for proving NPU offload status?
  • Within the session entry output, which specific line contains the offload verdict, and why is everything else secondary?
Q1 — MODEL ANSWER
get produces a clean operational summary prepared for administrators. diagnose exposes raw internal engine state. Priya needs evidence from inside the forwarding engine itself — not a summary. The session table lives under diagnose precisely because it shows what the engine is actually doing, not what an administrator-facing view interprets it to be.
Q2 — MODEL ANSWER
The npu info line is the verdict. It contains the offload=X/Y field which directly identifies which processor is handling each traffic direction. Everything else in the entry — proto, duration, src, dst, state flags — provides context about the session but says nothing about where processing is happening.
SECTION 01

Reading the Session Table Entry

diagnose sys session list is your primary tool for verifying NPU offload status. It lives under diagnose — not get — because it exposes raw internal engine state rather than an operational summary. When Priya asks for proof that trading sessions are hitting the NP7, this is the command and the npu info line is the answer.

FortiGate — annotated session entry
session info: proto=6 proto_state=01 duration=142 expire=3599
    → TCP session, established, running for 142 seconds

src=10.10.5.47 dst=172.16.1.20 src_port=52341 dst_port=443
    → Trading workstation to market data server over HTTPS

state=may_dirty os=6 ws=6 tos=0x00
    → Internal session state flags — noise for offload diagnosis

npu info: flag=0x81/0x81, offload=9/9, ips_offload=0/0
    → THE VERDICT LINE — both directions on NP7

The npu info line is where the proof lives. The state=may_dirty field and other session state flags are internal engine markers — important in some debugging contexts but not relevant to offload diagnosis. Train your eye to go straight to npu info.

You can use diagnose sys session filter before running the list command to narrow output to a specific source IP, destination IP, or port — essential in a production environment where the session table has thousands of entries.

Exam tip: The exam may show you a full session entry and ask you to identify offload status. Go straight to the npu info line. The offload=X/Y field is your answer. Everything else is context.
🧠
MENTAL NOTE
diagnose = raw engine. get = operational summary. Priya needs engine evidence, not a summary. The npu info line is the verdict — read it first, read everything else second.

💭 THINK FIRST · OFFLOAD VALUES

Marcus starred a session entry showing offload=9/9. He wasn't sure if this was good or bad. Before reading further — what do you think the number 9 represents, and what does the slash separate?

  • If 9/9 were a packet count for a session that has been running for 142 seconds on a trading floor — does that make sense? What does 9 actually represent?
  • What would you expect to see in the offload field for a session that is entirely CPU-bound?
Q1 — MODEL ANSWER
A 142-second trading session would have thousands of packets — so 9/9 cannot be a packet count. The number 9 is the internal processor code that FortiOS uses to identify the NP7. The slash separates the forward direction (source to destination) from the reverse direction (destination to source). offload=9/9 means both directions are being handled by the NP7.
Q2 — MODEL ANSWER
A fully CPU-bound session shows offload=0/0. Zero means no NPU processor is involved — both directions are being processed entirely in software on the CPU. This is the slow path.
SECTION 02

Decoding offload=X/Y

The offload=X/Y field contains two numbers separated by a slash. The first number represents the forward direction (source to destination). The second represents the reverse direction (destination to source). Each number is the internal processor code identifying which hardware is handling that direction of traffic.

ValueProcessorMeaningStatus
9NP7Direction handled by NP7 — fast path, CPU bypassedOFFLOADED
0CPUDirection handled by CPU — slow path, software processingNOT OFFLOADED

The most important combinations you will encounter in production and in the exam:

offload valueMeaningAction
offload=9/9Both directions on NP7. Full fast-path offload.This is what you want. No action needed.
offload=0/0Both directions on CPU. Full slow-path.Investigate. Read the no_ofld_reason field.
offload=9/0Asymmetric. Forward on NP7, reverse on CPU.Unusual. Investigate routing asymmetry.
Fully offloaded — what you want to see
npu info: flag=0x81/0x81, offload=9/9, ips_offload=0/0, epid=128/166...
Both directions = 9 = NP7. No no_ofld_reason line present. Done.
CPU-bound session — investigate further
npu_state=0x000001 no_offload
no_ofld_reason:  disabled-by-policy
Find this policy. Check: set auto-asic-offload disable
Common mistake: Engineers sometimes interpret offload=9/9 as "9 packets offloaded out of 9 total." A 142-second trading session would have thousands of packets. The number is a processor code, not a counter.
🧠
MENTAL NOTE
9 = NP7. 0 = CPU. The slash separates forward from reverse. offload=9/9 is your proof for Priya. offload=0/0 is the start of an investigation.

💭 THINK FIRST · CONSTRAINTS VS DECISIONS

Daniel asks whether any session flat-out cannot be offloaded regardless of policy. This is a harder question than it appears — it requires distinguishing between architectural constraints and configuration choices.

  • FTP uses a control connection on port 21 and then opens a second data connection on a dynamically negotiated port. Why does this prevent NP7 offloading, and what mechanism handles it instead?
  • If you see no_ofld_reason: helper in a session entry, should you try to fix it? Why or why not?
Q1 — MODEL ANSWER
The FTP data connection port is negotiated inside the application payload of the control connection. The NP7 is a forwarding engine — it moves packets based on headers and session keys. It cannot parse application payloads. FortiOS uses a session helper — software running on the CPU — to watch the control connection payload, extract the negotiated port, and dynamically create a pinhole. Because the helper must read payload continuously, the session cannot be handed to the NP7. It stays on the CPU for its entire lifetime.
Q2 — MODEL ANSWER
No. no_ofld_reason: helper is expected behaviour, not a problem. The protocol requires CPU involvement by design. Identify which protocol is involved, confirm a session helper is appropriate for it, and move on. Treating this as a performance problem to solve is wasted effort — and the kind of mistake the exam is designed to test.
SECTION 03

Constraints vs Configuration Decisions

Daniel's question has a precise answer. Some sessions cannot be NP7-offloaded regardless of how clean the policy is. These are architectural constraints — not configuration choices. Understanding this distinction is the difference between a productive investigation and wasted effort.

CategoryCan it be fixed?Examplesno_ofld_reason
Session Helpers CONSTRAINT FTP, SIP, H.323, TFTP — protocols with dynamic secondary connections negotiated in payload helper
Software Tunnel Interfaces CONSTRAINT GRE tunnels, SSL VPN — tunnel processing runs on CPU. IPsec is the exception. software-tunnel
Very Short-Lived Sessions CONSTRAINT DNS queries, ICMP — session completes before NP7 session key is ever used Session gone before key installed
Proxy-Based UTM Profile DECISION Any policy with a proxy-mode security profile attached disabled-by-profile
Explicit Policy Override DECISION Policy with set auto-asic-offload disable — classic forgotten troubleshooting override disabled-by-policy
Analogy

Think of the NP7 as a toll booth with an automatic RFID lane.

Once your car is registered (session key installed), you sail through without stopping. But some vehicles can never use the RFID lane — oversized trucks that need a weighbridge inspection (session helpers), vehicles on routes that bypass the toll entirely through a different road (software tunnels), or cars that arrive and leave before the RFID reader even wakes up (very short sessions). No amount of policy change moves those vehicles into the RFID lane.
Exam signal: When a question says "regardless of policy configuration," it is eliminating the two configuration decisions and pointing you toward the three architectural constraints. That phrase is a filter — use it.
🧠
MENTAL NOTE
Constraints cannot be configured away — helper, software-tunnel, and session-too-short are architectural. Decisions can be reversed — disabled-by-profile and disabled-by-policy are human choices. The no_ofld_reason field tells you which category you're in before you touch anything else.

💭 THINK FIRST · TROUBLESHOOTING

A junior engineer sends you a session list output showing offload=0/0 on the trading VLAN and says something is wrong. You have the output in front of you already — what is your first step before touching any other command?

  • What does the no_ofld_reason field tell you before you've opened a single other command, and why does that change what you do next?
  • What is the difference in response between no_ofld_reason: helper and no_ofld_reason: disabled-by-policy?
Q1 — MODEL ANSWER
The no_ofld_reason field immediately tells you whether you're dealing with an architectural constraint or a configuration decision — before you open any policy, any profile, or any other command. If it says helper or software-tunnel, the investigation is complete. Expected behaviour. If it says disabled-by-profile or disabled-by-policy, you have a configuration decision to trace. The reason code is the first filter, and it costs nothing because you're already looking at the output.
Q2 — MODEL ANSWER
helper — do not try to fix it. Identify the protocol, confirm a session helper is expected, move on. disabled-by-policy — find the matching firewall policy, look for set auto-asic-offload disable, and re-enable it. These are fundamentally different responses: one is acceptance of expected behaviour, the other is correcting a configuration error.
SECTION 04

The Offload Troubleshooting Methodology

When a session shows offload=0/0, the correct response is a structured three-step process. The session list entry already contains the first answer — you do not need another command to begin the diagnosis.

StepActionWhat you're doing
Step 1Read no_ofld_reason in the session entry you already haveCategorise: constraint or decision? This costs nothing — you're already there.
Step 2If constraint (helper / software-tunnel) — stopExpected behaviour. Document and move on. Do not chase it.
Step 3If decision — find the matching firewall policyCheck for proxy profile attachment or explicit auto-asic-offload disable.
no_ofld_reasonResponseNext command
helperEXPECTED — STOPNone. Identify protocol, confirm helper is correct, move on.
software-tunnelEXPECTED — STOPNone unless you can switch to IPsec.
disabled-by-profileINVESTIGATEFind the policy. Was proxy inspection intentional?
disabled-by-policyFIX ITFind the policy. Remove set auto-asic-offload disable.
Senior engineer instinct: Read the evidence you already have before reaching for another command. The no_ofld_reason field is your first filter. It eliminates entire categories of investigation in one glance.
Common trap: disabled-by-profile and disabled-by-policy look similar but have different root causes and different fixes. Profile means a proxy UTM profile is attached — change or remove the profile. Policy means auto-asic-offload was explicitly disabled — likely a forgotten troubleshooting override. Never confuse the two.
Verifying the fix — after removing proxy profile or re-enabling offload
# Clear existing sessions to force re-establishment
diagnose sys session clear

# Verify new sessions are offloaded
diagnose sys session list

# Look for:
npu info: flag=0x81/0x81, offload=9/9
# No no_offload or no_ofld_reason lines = success
🧠
MENTAL NOTE
Step 1 is always the reason code. It splits every investigation into two paths: expected behaviour (stop) or configuration problem (continue). The session entry you already have is the first diagnostic tool — not a stepping stone to another command.
