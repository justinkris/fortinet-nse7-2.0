One Router Bends the Rule, Everyone Else Follows

How route reflectors solve iBGP full-mesh scaling — and the two attributes that stop the loops it reopens.

Full mesh is not a suggestion — it is enforced by a rule that cannot bend on its own.

One router breaking that rule on purpose, safely, is the entire idea behind a route reflector.

Full Mesh Route Reflectors Loop Prevention Redundant RRs Confederations
💭 THINK FIRST · FULL MESH

eBGP stops loops with AS-PATH. Inside one AS, that tool can't work — the ASN never changes hop to hop. So what actually keeps an iBGP route from looping forever?

  • If Router A learns a route via iBGP from Router B, should A be allowed to pass that route on to Router C over another iBGP session?
  • If the answer is no, what does that force every iBGP router in the AS to do?
Q1 — MODEL ANSWER
No. iBGP split-horizon forbids it — an iBGP-learned route is never re-advertised to another iBGP peer, full stop.
Q2 — MODEL ANSWER
Every router needs a direct session to every other router, or the route dead-ends. That's full mesh — mandatory, not a best practice.
SECTION 01

Why iBGP Needs Full Mesh

eBGP prevents loops using AS-PATH: every time a route crosses an AS boundary, the ASN gets prepended, and a router rejects anything already carrying its own ASN. Inside a single AS this tool is blind — the ASN never changes hop to hop, so AS-PATH cannot detect a loop even in principle.

BGP's actual fix is structural, not clever: an iBGP-learned route is never re-advertised to another iBGP peer. Only eBGP-learned or locally-originated routes get forwarded into iBGP. Since propagation between iBGP peers is forbidden, every router needs a direct session to every other router just to receive all the routes — that's why full mesh is mandatory.

Common misconception: Full mesh isn't there because iBGP lacks a "flooding" mechanism like OSPF's LSDB — it's there because of a deliberate loop-safety rule that has no other workaround.

💭 THINK FIRST · ROUTE REFLECTORS

The split-horizon rule is fixed — no router should be able to just ignore it. Or should exactly one be allowed to, on purpose?

  • If one router were granted a scoped exception to split-horizon, what would the other routers need to do differently — peer with everyone, or just with that one router?
  • What do you think that one router should be called?
Q1 — MODEL ANSWER
Just with that one router. Clients no longer need sessions to each other — N-router mesh collapses to N sessions with a single hub.
Q2 — MODEL ANSWER
A route reflector (RR) — it "reflects" routes between its clients instead of forcing them to mesh directly.
SECTION 02

Route Reflectors — The Exception

A route reflector is an ordinary iBGP router granted one specific exception: for its designated clients, it is allowed to break split-horizon. It reflects a route learned from Client-A to Client-B and Client-C, and reflects routes learned from non-client peers to its clients too.

Clients only need a session to the RR, not to each other — an N-router mesh collapses to N sessions with one reflector. Client-side config is nothing special: a client is just an ordinary iBGP neighbor. It doesn't know it's a client.

FortiOS CLI — RR side
config router bgp
    set as 65100
    set router-id 172.16.1.1
    config neighbor
        edit "172.16.1.2"
            set remote-as 65100
            set route-reflector-client enable
        next
    end
end
Exam tip: route-reflector-client is configured per-neighbor on the RR only — never on the client side.
🧠
MENTAL NOTE
An RR is the split-horizon rule with one deliberate, scoped exception — nothing more. Know the rule first, then know exactly what's being excepted.

💭 THINK FIRST · LOOP PREVENTION

Breaking split-horizon reopens exactly the loop risk AS-PATH used to prevent. BGP needs two separate defenses here — one for the router that made the route, one for the RRs that pass it around.

  • What would let the originating router recognize "this route is mine, drop it" no matter how many RRs it bounced through?
  • What would let an RR recognize "I've already reflected this exact route once before"?
Q1 — MODEL ANSWER
Originator-ID — the originating router's RID is stamped onto the route the first time it's reflected. Seeing your own RID here means: discard.
Q2 — MODEL ANSWER
Cluster-List — an accumulating list of Cluster-IDs, prepended by every RR that reflects the route. An RR seeing its own Cluster-ID already in the list discards it.
SECTION 03

Loop Prevention: Originator-ID & Cluster-List

Originator-ID is stamped the first time a route is reflected, carrying the Router-ID of the originating router. Any router seeing its own RID here discards the route — protecting the original sender from re-accepting its own route. It's the BGP equivalent of OSPF's LSA originator check.

Cluster-List is the RR-layer equivalent of AS-PATH — an accumulating list, not a single tag. Every RR has a Cluster-ID (defaulting to its own RID) and prepends it every time it reflects a route. An RR checks incoming reflected routes for its own Cluster-ID already present; if found, discard. Only RRs stamp Cluster-List — clients never do.

Remember: these two attributes stop loops, not duplicates. A client with both a direct iBGP session and a reflected path to the same route just runs ordinary best-path selection between two valid paths — split-horizon already guarantees that route never gets forwarded back into the RR mesh.
🧠
MENTAL NOTE
Originator-ID protects the originator. Cluster-List protects every RR hop. Neither one is about resolving redundant paths — that's just normal best-path selection.

💭 THINK FIRST · REDUNDANT RRs

A single RR is a single point of failure. Adding a second RR to the same cluster for redundancy sounds simple — until you ask what happens to Cluster-List when there are two RRs instead of one.

  • If each RR defaults to using its own Router-ID as its Cluster-ID, what happens when RR1 reflects a route and RR2 later sees it?
Q1 — MODEL ANSWER
RR2 doesn't recognize its own Cluster-ID in the list (it's different from RR1's), so it re-reflects the route as if it were new — the loop-prevention check silently fails for the pair.
SECTION 04

Redundant Route Reflectors & Cluster-ID

For HA, a cluster can have two RRs (e.g. FG-EDGE-P and FG-CORE-1) serving the same clients. If each defaults to its own Router-ID as Cluster-ID, a route reflected by one and later reflected again by the other won't be recognized as "already seen" — it gets re-reflected as if new.

The fix: configure both RRs with the same cluster-id, making two physical routers look like one logical reflector to the Cluster-List check.

FortiOS CLI — shared cluster-id
config router bgp
    set cluster-id 10.10.10.10
end
Common misconception: cluster-id (a configured value, set once per RR) and Cluster-List (the accumulating attribute stamped on the route) are easy to conflate under exam pressure — they are not the same thing.
🧠
MENTAL NOTE
Redundant RRs in one cluster must share a cluster-id, or Cluster-List loop prevention silently breaks between them.

💭 THINK FIRST · CONFEDERATIONS

Route reflectors solve full-mesh by bending the split-horizon rule for one router. Confederations take the opposite approach — they change what "the AS" even means.

  • If links between sub-ASes inside a confederation behave like eBGP, what loop-prevention tool comes back into play automatically — the one iBGP couldn't use on its own?
Q1 — MODEL ANSWER
AS-PATH. Sub-AS boundaries act like real AS boundaries, so each one prepends its sub-AS number — loop prevention comes for free, no Originator-ID or Cluster-List required.
SECTION 05

Confederations — The Other Answer

Confederations split one AS (e.g. 65100) into private sub-ASes (65101, 65102...). Within a sub-AS: still iBGP, still full mesh — but small. Between sub-ASes: sessions behave like eBGP, and sub-AS numbers are stripped at the confederation boundary, so externally it's still one AS.

Because inter-sub-AS links act like eBGP, AS-PATH naturally provides loop prevention again — no Originator-ID or Cluster-List needed at all.

Route ReflectorOriginator-ID + Cluster-ListFlat AS, but new attributes needed

Exam tip: Know confederations exist and why they avoid Originator-ID/Cluster-List — RRs remain the dominant real-world design and the more heavily weighted exam topic.
🧠
MENTAL NOTE
Confederations trade AS-PATH's free loop protection for real AS-renumbering complexity. RRs stay flat but need purpose-built attributes to police the exception they create.
