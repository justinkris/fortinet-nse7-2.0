FGCP Fundamentals — Active-Passive

Election, monitored interfaces, virtual MACs, heartbeat mechanics, and every step the secondary takes in the first moments after the primary falls silent.

A failover isn't one event — it's a detection, an election, and a Layer 2 identity handoff, and the exam tests each stage separately.

At Vaultline Financial, a dead WAN circuit that nobody noticed, a reboot test that "shouldn't" have failed back, and a stubborn switch each exposed one stage of the machine. This guide reassembles the whole machine.

💭 THINK FIRST · INTERFACE MONITORING

Box A's WAN circuit to Clearing Partner 2 goes dark. Box A itself is healthy — CPU normal, heartbeat with Box B intact. The cluster does nothing. Marcus asks: is this now a silent single point of failure? The uncomfortable truth is buried in a default.

  • Before any engineer configures anything, does FGCP watch individual data interfaces at all — or is the heartbeat the only thing keeping the members honest?
  • If monitoring every interface protects against every link failure, why would an experienced engineer deliberately choose NOT to monitor everything?
Q1 — MODEL ANSWER
FGCP monitors nothing by default. Interface health is strictly opt-in: an engineer must explicitly add each interface to the monitored list (set monitor) before its up/down state feeds the election. Out of the box, only the heartbeat answers "is my partner alive?" — a dead WAN circuit on an otherwise healthy primary is invisible to the cluster.
Q2 — MODEL ANSWER
Monitoring everything makes the cluster hair-triggered. Every transient flap on any interface would count against the member's election standing, causing unnecessary failovers — each of which carries a real cost (the NP7 resync tax from Session 15). Monitor only the interfaces whose failure genuinely warrants moving the primary role.
SECTION 01

Monitored Interfaces Are Opt-In

The Vaultline incident that opened this session is the most common real-world FGCP misconfiguration: an HA pair that looks perfectly healthy while a business-critical circuit sits dead. The reason is simple and easy to forget — FGCP does not monitor any data interface by default. The only built-in liveness check is the heartbeat between members. Everything else must be declared explicitly:

FortiOS CLI — declaring monitored interfaces
config system ha
    set monitor "wan1" "wan2"
end

Once an interface is on the monitored list, its status feeds directly into the first and most decisive election criterion: the member with the most monitored interfaces in an up state wins the primary role. A monitored link failing on the primary therefore triggers a failover to a secondary whose equivalent link is still up — which is exactly the behaviour Marcus expected and didn't get.

Two important couplings follow. First, a symmetric failure changes nothing: if the same monitored interface is down on both members, both lose equally, the relative standing is unchanged, and no failover occurs — because failing over would fix nothing. Second, a monitored interface failure resets that member's HA uptime to zero, exactly as a reboot does. Interface monitoring and the uptime criterion are not independent facts; a box recovering from a link failure looks, to the election, like a box that just restarted.

Common misconception: "The cluster will notice if an important link dies." It will not — unless someone told it that link was important. Auditing the monitored list against the actual business-critical circuits is a deployment-review item, not an optional extra.
Remember: Don't monitor everything. Monitor the interfaces whose failure should move the primary role — typically the traffic-carrying WAN/LAN paths — and leave the rest out to avoid flap-driven failovers.
🧠
MENTAL NOTE
FGCP watches nothing by default. Interface monitoring is opt-in via set monitor; it feeds election criterion #1 (most monitored interfaces up), a monitored-link failure resets HA uptime to 0, and a symmetric failure on both members triggers no failover at all.

💭 THINK FIRST · ELECTION WATERFALL

Marcus reboots Box A (the primary) with override disabled. Box A returns 40 seconds later, fully healthy — and reclaims primary. Priya is confused: "I thought override off meant no preemption?" Her mental model has a hole in it, and the exam knows exactly where.

  • Box B had been primary for several minutes when Box A rejoined. Which election criterion should have kept Box B primary — and why didn't it?
  • If Box A had instead returned after 5 minutes and 1 second, who would be primary, and which criterion would decide it?
Q1 — MODEL ANSWER
HA uptime — but uptime only decides the election when the gap is at least 5 minutes. At 40 seconds, Box B's lead was under the threshold, so the uptime criterion produced no verdict and the election fell through to priority, where Box A's higher configured value won. Override never entered into it.
Q2 — MODEL ANSWER
Box B stays primary. By 5:01, Box B has banked a ≥5-minute uptime lead, so the uptime criterion resolves decisively in its favour and the waterfall stops — priority is never consulted. The counter-intuitive rule: a short outage lets the higher-priority box preempt via fallthrough; a long outage lets the survivor permanently outrun that preemption.
SECTION 02

The Election Is a Waterfall, Not a Number

Primary election is not "highest priority wins." It is an ordered list of criteria, and the process stops at the first criterion that produces a clear winner. Everything below the stopping point is ignored entirely. The order depends on the override setting:

StepOverride DISABLED (default)Override ENABLED
1Most monitored interfaces upMost monitored interfaces up
2Highest HA uptime (must lead by ≥5 min)Highest priority
3Highest priorityHighest HA uptime (≥5 min)
4Highest serial numberHighest serial number

HA uptime is a distinct clock — not system uptime. It counts continuous, healthy membership in the cluster and resets to zero on exactly two triggers: a reboot, or a monitored interface failing. It can also be reset deliberately with diagnose sys ha reset-uptime, which is the sanctioned way to force a failover with override disabled: zero the current primary's clock and the peer wins the uptime check on demand — a one-time, controlled action with no standing side effects. Inspect the state with diagnose sys ha dump-by vcluster: the member showing 0 in the uptime column has the lowest HA uptime, and reset_cnt counts how many times that member's clock has been zeroed.

The 5-minute margin exists for the reason you derived yourself: a box that flaps every 40 seconds should not keep winning elections. Under 5 minutes of difference, uptime is treated as noise and produces no verdict. This creates the trap of the session — the failback window. A briefly-absent higher-priority member walks straight back into the primary role (uptime tie → fallthrough → priority), while a long-absent one finds the door closed (survivor's uptime lead is decisive). Most engineers guess this exactly backwards.

Serial number is the final tiebreaker — always deterministic, guaranteeing the election can never deadlock. And critically, the full waterfall is a negotiation between members that can hear each other. When the primary dies outright and goes silent, there is no comparison to run: the survivor performs one self-check (its own monitored interfaces), confirms it is healthy, and declares primary unopposed. Lower priority is irrelevant when there is no rival left to outrank.

Exam tip: "Box A crashes; Box B has lower priority — does Box B take over?" Yes, always. The waterfall resolves ties between living members; it is not a qualification exam the survivor must pass.
🧠
MENTAL NOTE
Waterfall (override off): monitored interfaces → uptime (≥5 min to count) → priority → serial. Stops at the first clear winner. Uptime resets on reboot OR monitored-interface failure. Short absence = preemption via fallthrough; long absence = survivor keeps primary.

💭 THINK FIRST · OVERRIDE & FAILBACK

Priya wants Box A to be primary whenever it's healthy — no coin-flips of uptime timing. There's a setting that guarantees exactly that. The senior-engineer question is not whether it works, but what it costs every single time it fires.

  • What does enabling override actually change about the election — and what does it NOT change?
  • What price does the cluster pay, guaranteed, every time the preferred primary comes back online with override enabled? Connect it to Session 15.
Q1 — MODEL ANSWER
Override swaps the positions of uptime and priority in the waterfall — priority is checked second instead of third. It does not "enable" priority (priority participates either way) and it does not change criterion #1 or #4. With override on, the highest-priority healthy member always wins, regardless of uptime.
Q2 — MODEL ANSWER
A second, deliberate failover on every recovery — the preferred box takes its role back the moment it returns. Each failback re-triggers the NP7 resync tax from Session 15: every inherited session's first packet is CPU-punted to reprogram the fast path. Override means paying the resync cost twice per outage, by design.
SECTION 03

Override Changes the Order, Not the Rules

Priya's mental model — "override off means no preemption" — is the common oversimplification. The precise rule: override swaps the positions of priority and HA uptime in the election waterfall. With override enabled (CLI only: set override enable), priority is consulted before uptime, so the member you crowned with the highest priority value reclaims the primary role every time it is up and healthy.

The honest trade-off, straight from the study guide: with override enabled, a failover event is triggered when the primary fails and also when the primary becomes available again. Every recovery is a second failover — and thanks to the kernel-vs-silicon distinction from Session 15, every failback re-runs the NP7 resync: all inherited sessions CPU-punted, worst case 100% at once. That's not a pathological edge case; it's the designed behaviour, purchased deliberately in exchange for a deterministic primary.

Two further details the exam loves. First, override and priority are per-member settings that are never synchronized between cluster members — you must set them on each box individually, and forgetting one side is a classic misconfiguration. Second, with override enabled, the easiest way to force a failover is to change priorities (raise the secondary's or lower the primary's); with override disabled, the tool is diagnose sys ha reset-uptime on the current primary.

Real-world judgment (yours, and correct): leave override disabled, alert on failover events, investigate, then fail back deliberately with reset-uptime when you choose to. Deterministic preference is rarely worth an automatic double-resync per outage.
🧠
MENTAL NOTE
Override = swap uptime↔priority in the waterfall. Cost = a guaranteed second failover (and second NP7 resync) on every recovery. Override + priority are per-member and never synced. Manual failover: override on → change priority; override off → reset-uptime.

💭 THINK FIRST · VIRTUAL MAC & GARP

Box B has just won the election. Every client ARP cache and every switch MAC table on the LAN still points at where Box A used to be. Something at Layer 2 has to change in milliseconds — but if you think it's the clients' ARP caches, you've fallen into the trap.

  • If the MAC address associated with the cluster's IP never changes across a failover, what is the gratuitous ARP actually correcting?
  • Two independent FGCP clusters share the same L2 segment and the same group-id, but different group-names. Do they merge? Do they conflict? What exactly happens?
Q1 — MODEL ANSWER
Switch MAC address tables, not client ARP caches. Clients map IP→MAC and that mapping is unchanged (the virtual MAC is cluster property). Switches map MAC→port, and their entry for the virtual MAC still points at the old primary's port. The GARP forces every switch to relearn which port the virtual MAC now lives behind.
Q2 — MODEL ANSWER
They do not merge — cluster membership requires group-id, group-name AND password all to match, and the group-name differs. But they DO conflict: the default virtual MAC formula uses group-id (plus vcluster ID and interface index), never group-name. Same group-id + same interface numbering = identical virtual MACs on two unrelated clusters — a silent L2 identity fight with no HA alarm, presenting as flaky switching.
SECTION 04

Virtual MAC: the Identity Belongs to the Cluster

When the primary joins the cluster, every interface — except HA heartbeat interfaces and reserved management interfaces — is assigned a virtual MAC address, and the primary informs the secondary of the full set. At failover, the new primary silently adopts the identical virtual MACs for its equivalent interfaces. The identity never "moves" because it was never tied to a box: it is cluster property. Client ARP caches (IP→MAC) therefore never go stale.

What does go stale is every switch's MAC address table (MAC→port). The new primary's gratuitous ARP broadcasts exist for exactly one job: force switches in the path to relearn which port the virtual MAC now sits behind. Some high-end switches are stubborn and keep forwarding to the old port anyway; the fix is set link-failed-signal enable, which makes the former primary shut all its interfaces (except heartbeat and reserved management) for one second at failover — faking a physical link-down that flushes even stubborn MAC tables the hard way.

Virtual MAC assignment has three methods, highest priority first: manual per interface (set virtual-mac under the interface), automatic per interface (set auto-virtual-mac-interface — hardware MAC with the Universal/Local bit flipped, e.g. 04→06 in the first octet), and the default: group-ID-based calculation for all interfaces. The default formula encodes three inputs into the MAC — group ID, virtual-cluster ID, and the interface's physical index — via one of four logic tables (prefixes like 00:09:0f:09 for logic 2 and e0:23:ff for logics 1/4, depending on whether group-id > 255, physical index > 127, or vclusters are in play). You verify with diagnose hardware deviceinfo nic <port>: Hwaddr shows the current (virtual) MAC, Permanent Hwaddr the burned-in one.

This is why group-id does double duty: it is both a cluster-membership credential (must match, alongside group-name and password) and a mathematical ingredient of the virtual MAC. Group-name is credential only — required to match, but never computed into anything. Hence Fortinet's hard rule: two clusters in the same broadcast domain must use different group IDs, or they will compute colliding virtual MACs no matter how different everything else is.

Nasty failure mode: colliding virtual MACs between two healthy, independent clusters produce no HA alarm. Symptoms look like random intermittent connectivity — the same source MAC flapping between two switch ports. If two clusters share an L2 segment, check group IDs before anything else.
Analogy

The virtual MAC is a company phone number, not a personal one.

  • Customers (clients) dial the same number (virtual MAC) forever — their address books (ARP caches) never change.
  • When the on-call engineer changes (failover), the switchboard (switch MAC table) must be told which desk (port) the number now rings at — that's the GARP.
  • If two companies accidentally register the same number (same group-id, same segment), callers randomly reach the wrong office — and neither company's own systems report a fault.
🧠
MENTAL NOTE
Virtual MAC = cluster property, adopted unchanged by the new primary (all interfaces except heartbeat + reserved mgmt). GARP fixes switch MAC→port tables, never client ARP. Default vMAC formula inputs: group-id + vcluster ID + physical index — group-name is never an input. link-failed-signal fakes a 1-second link-down for stubborn switches.

💭 THINK FIRST · HEARTBEAT & FAILOVER SEQUENCE

Everything this session built — election, virtual MAC, GARP — rests on one substrate: the two boxes hearing each other. Lose that with no backup, and something far worse than a failover happens: two primaries at once, both claiming the same virtual MACs on the same wire.

  • Vaultline configures set hbdev "port3" 10 "port4" 20. Which port carries the heartbeat right now, and what happens if it fails? Is heartbeat traffic ever load-balanced across both?
  • Box A loses power at T=0. Using the defaults, roughly when does Box B declare it dead, and what is the complete ordered sequence from that moment until traffic flows through Box B?
Q1 — MODEL ANSWER
Port4 (priority 20 — higher number wins). If it fails, the cluster falls to port3. Heartbeat is a strict priority-ordered failover list — one active path, never load-balanced. Contrast with session-sync-dev, which IS load-balanced across multiple interfaces because it carries bulk session data, a different job entirely.
Q2 — MODEL ANSWER
Defaults: hb-interval 200 ms × hb-lost-threshold 20 = ~4 seconds to declare failure. Sequence: (1) hello packets (EtherType 0x8890/0x8891) stop arriving; (2) threshold expires, Box B declares Box A dead; (3) no election race — Box B self-checks its own monitored interfaces and declares primary unopposed; (4) Box B adopts the identical virtual MACs; (5) Box B broadcasts gratuitous ARPs; (6) switches relearn MAC→port; traffic flows. Inherited sessions then pay the NP7 resync tax as they re-offload.
SECTION 05

Heartbeat Mechanics and the Failover Sequence

The heartbeat consists of hello packets — Layer 2 Ethernet frames using proprietary EtherTypes 0x8890 and 0x8891 (config sync uses 0x8893) — never 0x0800 (IP) and never 0x8100 (dot1Q VLAN tagging, an unrelated technology worth explicitly not confusing). Each hello carries the sender's state: alive, uptime, priority, monitored-interface status. Because this is pure L2, heartbeat interfaces must share a broadcast domain or connect directly; a routed hop silently kills the cluster. Sniff it with diagnose sniff packet any "ether proto 0x8890" 4.

Detection math: by default a hello is sent every hb-interval of 200 ms, and a member is declared dead after hb-lost-threshold = 20 consecutive misses — roughly 4 seconds. Both are tunable: lower for faster detection (risking false positives from a busy-but-alive peer), higher for safety. Best practice is at least two heartbeat interfaces, each with an explicit priority in hbdev (higher value wins), forming an ordered, exclusive failover list. A backup-hbdev can additionally be reserved specifically for the split-brain case — the exact scenario where a heartbeat-less secondary would otherwise promote itself while the primary still lives, producing two primaries sourcing the same virtual MACs on the same wire plus diverging configs (config sync also rides the heartbeat).

The complete failover sequence — the capstone of the session, in strict order:

  1. Silence: hello packets (0x8890/0x8891) stop arriving on Box B's active heartbeat interface.
  2. Declaration: after hb-lost-threshold × hb-interval (default ≈ 4 s), Box B declares Box A failed.
  3. Self-check, not a race: with no living rival, there is nothing to compare. Box B verifies its own monitored interfaces and declares primary unopposed — its priority and serial are irrelevant.
  4. Identity adoption: Box B assumes the identical virtual MAC set on all equivalent interfaces.
  5. GARP: Box B broadcasts gratuitous ARPs so every switch relearns which port each virtual MAC lives behind (link-failed-signal available for stubborn switches — moot here, since Box A is powered off and its links are already down).
  6. Traffic + resync: frames flow to Box B; kernel sessions were already synced, and each inherited session's first packet is CPU-punted to program Box B's NP7 (Session 15's resync tax).
Exam tip: heartbeat = ordered/exclusive (hbdev priorities, one active path); session-sync-dev = load-balanced (bulk data). Two similar-looking multi-interface configs, two different jobs. Fortinet loves testing whether you conflate "dedicated for redundancy" with "load balanced."
🧠
MENTAL NOTE
Hellos on 0x8890/0x8891 (config sync 0x8893), default 20 lost × 200 ms ≈ 4 s to declare death. Dead-silent primary → survivor self-checks and declares, no election race. Then: adopt vMACs → GARP → switches relearn → traffic → NP7 resync. Split-brain = two primaries claiming the same vMACs; two heartbeat links is load-bearing best practice.
