🍪 Study Nibble · <2 min · Session 16

link-failed-signal — When GARP Isn't Enough

Some high-end switches ignore the gratuitous ARP and keep forwarding to the former primary's port. link-failed-signal fakes a physical link failure — a language every switch is forced to understand.
💀
Failover happens
New primary adopts the virtual MACs and broadcasts gratuitous ARPs so switches relearn MAC→port.
↓
🙉
The problem: the stubborn switch
Some high-end switches don't clear their MAC tables correctly after receiving the GARPs — they keep sending frames for the virtual MAC to the former primary's port. Traffic falls into a black hole.
↓
🔌
The fix: fake a link failure
With link-failed-signal enabled, the former primary shuts down all its interfaces for one second during failover — except heartbeat and reserved management. Every switch sees a real link-down event and is forced to flush the related MAC table entries the hard way.
FortiOS CLI — default is disable
config system ha
    set link-failed-signal enable
end
Remember the actor: it's the old primary that drops its links — not the new one. And it only helps when the old primary is still alive (planned failover, monitored-link failover). If it lost power outright, its links are already physically down, which flushes the switches anyway.
Exam angle: "After failover, some traffic still reaches the former primary despite gratuitous ARPs — what fixes it?" → link-failed-signal. Distractors will offer client-side fixes (ARP timers, static ARP) — wrong layer: the stale entry lives in the switch's MAC table, not any ARP cache.
