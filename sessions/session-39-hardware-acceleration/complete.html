Section 01

Why Hardware Acceleration Exists

A general-purpose CPU was never designed to inspect millions of network packets per second while simultaneously running an operating system, maintaining session tables, evaluating firewall policies, and running threat detection engines. Under high throughput, the CPU becomes the bottleneck — and in enterprise environments, that bottleneck costs latency, drops sessions, and reduces security effectiveness.

Fortinet's answer is the same principle that transformed switching: purpose-built silicon for purpose-built tasks. Just as a switch ASIC handles MAC address lookups at wire speed without touching the switch CPU, Fortinet's SPU (Security Processing Unit) handles specific security tasks at hardware speed without touching the firewall CPU.

🏢 The Vaultline Lesson

One policy change. 3 AM. CPU at 94%.

Vaultline Financial's trading VLAN ran at sub-millisecond latency because market data sessions were offloaded to the NP7. A single "quick security improvement" — adding a proxy-based profile to the policy — forced every one of those sessions onto the CPU slow path. Latency spiked to 8–12ms. The lesson: hardware acceleration is not a background feature. It is the architecture. Understanding it is mandatory for every enterprise firewall design decision.

Section 02

The Four Processors

High-end FortiGate devices separate network and content processing onto dedicated chips. Entry-level devices integrate both onto a single chip. Understanding which device has which silicon is essential for both design and exam scenarios.

NP7 — Network Processor
FortiGate 900G · Latest generation
  • Session forwarding — fast path
  • NAT (source and destination)
  • IPsec VPN encryption / decryption
  • ACL, HPE, IP integrity header checking
  • Up to 12 million sessions
  • Bypasses CPU after session key installed
  • Works with flow-based profiles via NTurbo
CP9 / CP10 — Content Processor
FortiGate 200G+ · Coprocessor to CPU
  • Pattern matching via IPSA
  • SSL/TLS encryption and decryption
  • IPsec Diffie-Hellman key exchange
  • Works in both flow and proxy modes
  • CPU determines what gets offloaded
  • Advanced IPSA mode by default (except single CP8)
SP5 / SoC4 — Integrated Chip
FortiGate 90G / 91G · Branch devices
  • NP + CP functions on one chip
  • Lower throughput than dedicated NP7 + CP9
  • Designed for branch and mid-range
  • IPS engine still runs on CPU
  • Never position as VPN hub
  • SoC4 = most constrained (entry-level)
CPU — Main Processor
All FortiGate models · Always present
  • Orchestrates all processing
  • Mandatory for proxy-based inspection
  • Mandatory for session helpers
  • Mandatory for SSL VPN / GRE tunnels
  • Handles FIN / RST packets always
  • Handles first TCP handshake always
Identify your silicon: diagnose hardware lspci | grep 1a29 — NPID 4e36 = NP6, NPID 4e37 = NP7. For CP and SP: get hardware status — review ASIC version field.

Section 03

Fast Path vs Slow Path

Every session begins on the slow path. The CPU always processes the first TCP three-way handshake (or first UDP packet) to determine whether offload conditions are met. If they are, the session key is installed in the NP7 and subsequent packets bypass the CPU entirely — the fast path.

PathWho Handles ItWhenPerformance
Slow pathCPUAlways — first packets of every session. Also all proxy sessions, helpers, software tunnels.Lower throughput — CPU bound
Fast pathNP7After session establishment — when offload conditions are metWire-speed — CPU not involved
NTurbo pathNP7 + IPS + CP9Flow-based security profiles active — NTurbo bridges NP7 to IPS engineAccelerated — CPU orchestrates only

FIN and RST packets are always handled by the CPU regardless of which path the session data is taking. This is normal and expected.

Critical Distinction
NTurbo is a transport optimisation — not a security feature. Disabling it never changes what the IPS engine inspects. It only changes how expensively packets get there. Same signatures. Same detection. Worse performance.
IPSA modes: Basic mode offloads standard pattern matching (default on devices with one CP8). Advanced mode offloads more pattern matching types (default on all other devices). Configure under config ips global → set cp-accel-mode.

Section 05

The Four Slow Path Triggers

Even when NP acceleration is enabled on a policy, four conditions force sessions to the CPU slow path. Memorise these — the exam tests them frequently and in combination.

  • 1
    Proxy-Based Security Profiles
    Any proxy-based profile on a policy forces the entire session to the CPU. The NP7 cannot buffer and reassemble full traffic streams — that fundamentally requires the CPU to remain in the loop for every packet.
  • 2
    Session Helpers Required
    Protocols like FTP, SIP, and PPTP negotiate dynamic secondary connections inside the application payload. FortiOS uses software session helpers to track this negotiation and open dynamic pinholes. The CPU must stay involved for the entire session — the NP7 cannot do application-layer protocol tracking.
  • 3
    Tunnelled Interfaces — Except IPsec
    SSL VPN and GRE are software-defined logical interfaces managed entirely by the CPU. The NP7 cannot take over sessions on software tunnel interfaces. IPsec VPN is the exception — the NP7 has dedicated hardware crypto engines that natively handle IPsec encryption and decryption.
  • 4
    NP Acceleration Explicitly Disabled
    Setting np-acceleration disable on a firewall policy is a direct hardware override. All sessions matching that policy go to the CPU regardless of their profile type. Used legitimately for troubleshooting packet captures — dangerous if left enabled in production.

Section 06

The Mixed Policy Trap

This is the most exam-tested concept in the entire hardware acceleration domain. When a firewall policy contains both flow-based and proxy-based profiles, there is no splitting of work between NP7 and CPU.

🚨
All or nothing: Any proxy-based profile on a policy forces the entire session to the CPU slow path. The NP7 is excluded completely — not partially. A policy with flow-based IPS and proxy-based DLP = CPU only for every session.

The hidden version of this trap: some features are inherently proxy-only even when the policy inspection mode is set to flow-based. Adding them silently forces the entire policy to proxy mode.

VoIP InspectionProxy-onlyEntire policy forced to proxy — NP7 offload lost
AntispamProxy-onlyEntire policy forced to proxy — NP7 offload lost

Application ControlFlow-basedCompatible with NP7 via NTurbo
Antivirus (flow mode)Flow-basedCompatible with NP7 via NTurbo
Antivirus (proxy mode)Proxy-onlyEntire policy forced to proxy — NP7 offload lost
Design solution: Split policies by inspection requirement. High-volume, latency-sensitive traffic gets a dedicated flow-based policy. Traffic requiring proxy-based features gets a separate policy. Never mix them on the same policy if performance matters.

Section 07

SP5 and SoC4 — Branch Silicon

Entry-level and mid-range FortiGate devices replace the separate NP7 and CP9 with a single integrated chip — the SP5 (also called SoC5) or SoC4. This reduces cost, power consumption, and physical size — making it suitable for branch office deployments.

CharacteristicNP7 + CP9 (High-End)SP5 / SoC4 (Branch)
ArchitectureSeparate dedicated chipsIntegrated single chip
ThroughputVery high — parallel processingLower — shared silicon
Session capacityUp to 12M sessions (NP7)Significantly lower
IPsec VPNHardware offloaded — NP7 crypto enginesHardware offloaded — integrated
IPS engineSoftware on CPU — bridged via NTurboSoftware on CPU — same challenge
Deployment roleData centre, campus core, VPN hubBranch office, remote site only
Example deviceFortiGate 900GFortiGate 90G / 91G
Design warning: Never position a SoC4 device as a hub in a hub-and-spoke VPN topology. It lacks the dedicated NP7 crypto engines and session capacity required to terminate multiple IPsec tunnels while maintaining throughput. The hub becomes the bottleneck for the entire network.

Section 08

Troubleshooting Hardware Acceleration

The primary diagnostic tool for confirming whether a session is offloaded is the session list. This is your first stop whenever you suspect a performance issue caused by unexpected slow-path processing.

Confirm NP7 offload status
diagnose sys session list

# Offloaded session — look for:
npu info: flag=0x81/0x91, offload=9/9, ips_offload=0/0
# Code 9 = NP7

# Not offloaded — look for:
npu_state=0x000001 no_offload
no_ofld_reason: disabled-by-policy
Confirm IPsec SA offload status
diagnose vpn tunnel list name <tunnel-name>

# npu_flag=00  Both SAs in kernel — not yet offloaded
# npu_flag=01  Outbound SA copied to NPU
# npu_flag=02  Inbound SA copied to NPU
# npu_flag=03  Both SAs offloaded — fully accelerated
# npu_flag=20  Unsupported cipher — cannot offload
Temporarily disable offload for packet capture
config firewall policy
    edit <policy_id>
        set np-acceleration disable   # Forces to CPU — sniffer can now see traffic
    next
end
# Run your capture, then immediately re-enable:
        set np-acceleration enable
Disable NTurbo globally (troubleshooting only)
config ips global
    set np-accel-mode none     # Disables NTurbo globally
    set cp-accel-mode none     # Disables IPSA globally
end
# Default values: np-accel-mode basic, cp-accel-mode advanced
Troubleshooting workflow: Suspect slow path → confirm with session list → identify no_ofld_reason → address root cause → verify offload restored. Never leave np-acceleration disabled after troubleshooting.

Section 09

Exam-Critical Notes

🚨
Most tested concept: Mixed flow + proxy policies. The exam expects you to know that any proxy profile kills NP7 offloading for the ENTIRE session — not just the proxy portion.
🚨
Common misconception: Flow-based inspection only reads headers. Wrong. Both modes read full Layer 7 payload. The difference is TIMING — flow acts in real time, proxy buffers the complete stream first.
🚨
IPsec exception: IPsec VPN CAN be offloaded to the NP7. SSL VPN and GRE cannot. Know this cold — the exam tests it as a distractor.
🚨
NTurbo misconception: Disabling NTurbo does NOT improve security. It is a transport optimisation. The IPS engine runs the same signatures regardless. Disabling NTurbo only degrades performance.
🚨
CP9 in proxy mode: Even when proxy mode forces sessions to the CPU, the CP9 can still offload SSL/TLS crypto. The NP7 is excluded — the CP9 is not.
🚨
SoC4 as hub: A common exam trap is positioning entry-level SoC4 devices as VPN hubs. The correct answer is always that this is a design error — SoC4 lacks the NP7 session capacity and dedicated crypto engines for hub roles.
