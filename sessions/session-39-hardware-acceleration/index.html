Session 39 — Hardware Acceleration — NP, CP, SP & SoC

Where we are in the NSE7 journey:
The CPU is the bottleneck on every firewall. Fortinet's answer is purpose-built silicon: NP (network), CP (content), SP (security), and the SoC integrations on lower models.

The problem we're solving today:
Hardware acceleration is a top-tier NSE7 domain. The exam expects you to know which features offload onto which processor and what forces the slow path.

Session goal:
For a given firewall policy, predict whether traffic offloads to NP/CP/SP or falls back to the kernel slow path.

Key concepts:
  • NP6 / NP7 — session forwarding, IPsec, NAT
  • CP9 — signature matching, SSL crypto
  • SP / ISF — low-latency switching at the chassis
  • SoC4 — entry-level integration on branch FortiGates
  • Slow path triggers (proxy mode, session helpers, complex NAT)

The session opened at 2:47 AM with a call from Marcus, the NOC engineer on overnight shift. The trading floor reported latency spikes from under 1ms to 8–12ms. Firewall CPU was sitting at 94%. A "quick security improvement" had been pushed to the trading VLAN firewall policy shortly before the incident.

Through structured investigation the student identified that a proxy-based security profile had been added to a previously flow-based policy, forcing all trading VLAN sessions off the NP7 fast path and onto the CPU slow path. A junior engineer scenario was introduced — someone who disabled NTurbo globally claiming it would "improve security." Concepts Learned

1Why Hardware Acceleration Exists

The CPU cannot sustainably handle every packet in a high-throughput enterprise environment. Fortinet built purpose-built silicon (SPU — Security Processing Unit) to offload specific tasks from the CPU. This is the same principle as switch ASICs — dedicated hardware for dedicated functions.

2The Three Processor Types (High-End)
  • NP7 (Network Processor): Works at the interface level. Handles session forwarding, NAT, IPsec encryption/decryption, ACL, HPE, and IP integrity checking. Supports up to 12 million sessions. Once the session key is installed, subsequent packets bypass the CPU entirely.
  • CP9/CP10 (Content Processor): Acts as a coprocessor to the CPU. Handles pattern matching for flow-based UTM (via IPSA), SSL/TLS encryption and decryption for deep inspection, and IPsec Diffie-Hellman key exchange. Works in both flow and proxy modes.
  • CPU: Orchestrates everything. Mandatory for proxy-based inspection, session helpers, and software tunnel interfaces.
3NTurbo

NTurbo is a dedicated driver that bridges the NP7 and the IPS engine when flow-based security profiles are active. Without NTurbo, adding any security profile would force the entire session to the CPU. NTurbo creates a special data path: NP7 → NTurbo driver → IPS engine → NTurbo driver → NP7. The CPU orchestrates but does not bottleneck forwarding. NTurbo is a transport optimisation — not a security feature.

4IPSA (IPS Acceleration)

When packets reach the IPS engine via NTurbo, IPSA offloads pattern matching to the CP9. Advanced mode (default on most devices) offloads more pattern matching types than basic mode. Devices with only one CP8 are limited to basic mode.

5Fast Path vs Slow Path
  • Fast path: Traffic handled by NP7, bypassing the CPU after session establishment.
  • Slow path: Traffic handled by the CPU. Always used for the first TCP handshake (3-way) or first UDP packet. Also used whenever offload conditions are not met.
6Four Slow Path Triggers — NP7 Will Not Offload When:

1. Proxy-based security profiles are on the policy

2. The session requires a FortiOS session helper (FTP, SIP, PPTP etc)

3. Tunnelled interfaces are involved — SSL VPN, GRE (IPsec VPN is the exception)

4. NP acceleration is explicitly disabled on the policy (np-acceleration disable)

7The Mixed Policy Rule

A firewall policy containing both flow-based and proxy-based profiles never offloads to the NP7. It is all or nothing. The proxy requirement always wins. Some features are inherently proxy-only (web category quota, certain DLP options, VoIP inspection) and silently force proxy mode even on an otherwise flow-based policy.

8SP5 and SoC4

For entry-level and mid-range devices, Fortinet integrates NP and CP functions onto a single chip — the SP5 (also called SoC5) and SoC4. This reduces cost, size, and power consumption. The trade-off is lower throughput and session capacity compared to dedicated NP7 + CP9. SoC4 devices are designed for branch deployments and should never be positioned as hubs in large hub-and-spoke topologies.

9Session Helpers

Protocols like FTP open secondary dynamic connections. The port for the secondary connection is negotiated inside the application payload of the control connection. FortiOS uses session helpers — software running on the CPU — to track this negotiation and dynamically open pinholes. Any session requiring a helper cannot be offloaded to the NP7.

Troubleshooting Experience

Fault Scenario: Vaultline Financial — Trading floor latency spike, CPU at 94%

Troubleshooting Process

1. Connected CPU spike to recent policy change — causal reasoning

2. Formed hypothesis: proxy-based inspection forced sessions to slow path

3. Identified verification command: diagnose sys session list — look for no_offload and no_ofld_reason fields

4. Confirmed hypothesis before touching configuration

5. Identified rollback as immediate fix — removed proxy-based profiles

6. Proposed split-policy architecture as sustainable long-term solution

Key Lessons
  • Always investigate before changing. Confirm the hypothesis with CLI evidence first.
  • diagnose sys session list is the primary tool for confirming NP7 offload status
  • npu info: offload=9/9 confirms NP7 offloading (code 9 = NP7)
  • no_ofld_reason: disabled-by-policy confirms explicit policy override
  • Always re-enable np-acceleration after troubleshooting packet captures
Mistakes to Avoid
  • Never disable NTurbo globally in production — even temporarily without a plan to re-enable
  • Never assume a mixed policy splits work between NP7 and CPU — it doesn't
  • Never position SoC4 devices as VPN hubs in large topologies

Important Takeaways

1The difference between flow-based and proxy-based is TIMING, not depth. Both read Layer 7. Only proxy buffers the complete stream before deciding.
2Any proxy-based profile on a policy kills NP7 offloading for the ENTIRE session — not just the proxy portion. All or nothing.
3NTurbo is a transport optimisation, not a security feature. Disabling it never improves what gets inspected.
4Four slow-path triggers: proxy profiles, session helpers, software tunnels (not IPsec), explicit disable.
5IPsec VPN is the one tunnel exception — NP7 has native crypto engines for it.
