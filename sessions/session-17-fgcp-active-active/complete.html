Active-Active Load Balancing

Why the secondary FortiGate isn't the idle-capacity fix it looks like — and exactly what crosses the wire between the two boxes.

A-A does not split traffic across two boxes — it lends Box A's CPU-expensive work to Box B, one session at a time.

Every endpoint still talks to Box A first. What changes in A-A is what happens to a session after it's matched — and that difference is where most NSE7 candidates get tripped up.

What Gets Balanced The Relay Asymmetric Path Worth It?
💭 THINK FIRST · WHAT GETS BALANCED

Box B sits at single-digit CPU while Box A carries the whole load. The obvious fix looks like flipping to Active-Active. Before accepting that, work out what actually happens to a plain HTTPS session — no UTM profile, just a firewall policy doing flow-based forwarding — the instant A-A is enabled.

  • A plain firewall-policy session (no UTM) arrives at the cluster. In A-A mode, does it get processed by whichever box has spare CPU, or does it stay exactly where it would in A-P?
  • Why would FortiGate bother distributing one category of session and not another — what's actually expensive enough to be worth the overhead of handing it to a second box?
Q1 — MODEL ANSWER
It stays on the primary. Only the primary owns the vMAC, so all ingress traffic lands there regardless of mode. By default, only sessions subject to proxy-based UTM inspection are distributed to the secondary — flow-based and no-inspection sessions never leave the primary unless load-balance-all is explicitly enabled.
Q2 — MODEL ANSWER
Plain policy matching, NAT, and flow-based inspection are cheap — largely NP-offloaded, microseconds of CPU. Proxy-based inspection (proxy AV, DLP, explicit web proxy) has to buffer and terminate the session, which is genuinely CPU/memory expensive. That's the only work worth the cost of shipping to a second box.
SECTION 01

What Active-Active Actually Distributes

Only proxy-inspected sessions leave the primary — everything else stays put.

Active-Active does not divide the cluster's total traffic in half. Every packet from every endpoint still arrives at the primary's virtual MAC — that never changes between A-P and A-A. What A-A adds is a distribution step that happens after the firewall policy match, and only for one category of session.

By default, FortiOS only distributes sessions that are subject to proxy-based inspection — proxy AV, DLP, explicit web proxy, and similar features that require the session to be buffered and effectively terminated for inspection. Flow-based inspection and plain flow-based policies (the bulk of most firewalls' traffic) are cheap enough that FortiOS doesn't bother distributing them — unless you force it with the load-balance-all setting.

🧠
MENTAL NOTE
A-A load-balances proxy-based UTM sessions only, by default. Plain flow-based traffic — the majority of most firewalls' load — never leaves the primary unless load-balance-all is explicitly enabled. If a candidate's traffic mix is mostly flow-based, flipping to A-A buys almost nothing.

💭 THINK FIRST · THE RELAY

A session is eligible for offload. The primary has to physically hand a live, in-progress packet to the secondary. That's not the same job as session-sync-dev, which just mirrors the session table for failover continuity — this is active, real-time forwarding of a session the primary is still alive and responsible for.

  • Is the mechanism carrying this forwarded traffic the same session-sync-dev link used for HA session-table mirroring, or something else entirely?
  • If the decision of which box handles a session has to be made once and stay fixed for the life of that session, what can the primary hash on to guarantee a consistent, stable result?
Q1 — MODEL ANSWER
Something else. FGCP traffic — including this forwarding — rides over the HA heartbeat interconnect, but uses Ethernet type 0x8891, distinct from the 0x8890 hello frames and completely separate from session-sync-dev, which mirrors the session table for standby failover continuity, not live session forwarding.
Q2 — MODEL ANSWER
The 4-tuple: source IP, destination IP, source port, destination port. These are the only header fields guaranteed identical on every packet of a TCP session from SYN to FIN. Hashing on anything that varies per-packet (like the IP Identification field) would scatter one session's packets across boxes mid-stream, which is impossible to reconcile.
SECTION 02

How the Handoff Actually Happens

0x8891 frames ride the heartbeat link but carry real session data, not hello packets.

images/s2-the-relay-mechanism.png
Flat minimalistic but highly detailed cartoon illustration, warm modern colour palette, cream background, coral accents, muted gold highlights, sage greens, soft brown outlines, no gradients, no 3D. Two FortiGate boxes connected by a single labelled cable marked 'heartbeat link'. Two small parallel lanes travel along the cable: one lane carries tiny heart-shaped icons labelled '0x8890 hello', the other carries small envelope icons labelled '0x8891 forwarded session' moving from Box A toward Box B. A separate, clearly distinct dashed cable below is labelled 'session-sync-dev — table mirror only', visually disconnected from the forwarding lane to show it's a different job. Clean bold line work, generous spacing.

The offload decision happens once, at the SYN, because that's the earliest point where a policy match exists and the only guaranteed-stable identifier — the 4-tuple — is available. FortiOS hashes on this 4-tuple (or a variant of it, depending on the configured schedule) to pick a secondary and keeps that mapping fixed for the life of the session. This is per-session distribution, not per-packet load balancing.

The actual forwarded packet travels over the same physical interconnect as heartbeat, but as a distinct Ethernet type — 0x8891 — separate from the 0x8890 hello frames and entirely separate from session-sync-dev (which only mirrors session-table state for failover, and is a passive backup copy, not live traffic). Confusing these three is one of the most common exam distractors in this topic.

🧠
MENTAL NOTE
Three distinct jobs, easy to conflate: 0x8890 = heartbeat hello (alive/dead, election). 0x8891 = FGCP traffic redistribution (the actual A-A session forwarding). session-sync-dev = passive session-table mirroring for failover, unrelated to A-A forwarding. The offload decision itself is a one-time 4-tuple hash at the SYN — never re-evaluated mid-session.

💭 THINK FIRST · ASYMMETRIC PATH

The natural assumption is that once Box B finishes inspecting a session, it hands the result back to Box A, which forwards it out — a clean round trip through the primary. For proxy-based sessions, that assumption is wrong, and the real behaviour is one of the most-tested nuances in this whole topic.

  • If you ran a packet capture on Box A's interface for a proxy-inspected session that completed successfully, what would you actually see?
  • What does this mean for how you troubleshoot a session that looks 'stuck' or 'dropped' on the primary in an A-A cluster?
Q1 — MODEL ANSWER
Every inbound packet of the session (client→cluster and server→cluster) with no replies visible. Endpoints keep addressing the cluster's vMAC — their ARP caches are unchanged — so Box A receives and relays every inbound packet to Box B via 0x8891. But every outbound packet is sent by Box B directly from its own physical MAC, so Box A never sees a single reply.
Q2 — MODEL ANSWER
A single-box capture is not trustworthy evidence in A-A. A SYN with no visible reply on Box A does not mean the session failed — it may have completed perfectly on Box B. Diagnosing a session in an A-A cluster requires knowing to check both boxes, not just the primary where the traffic first arrived.
SECTION 03

The Asymmetric Return Path

After the handoff, Box B owns the rest of the conversation — Box A never sees it again.

images/s3-asymmetric-path.png
Flat minimalistic but highly detailed cartoon illustration, warm modern colour palette, cream background, coral accents, sage greens, soft brown outlines, no gradients, no 3D. A network engineer stands in front of a monitor showing a packet capture window with a single lonely SYN packet and a large question mark, captured from 'Box A'. Behind them, a second smaller inset screen shows Box B calmly completing a full green checkmarked TCP handshake with a client icon and a server icon, with dashed direct-connection lines bypassing Box A entirely. Engineer has a puzzled but curious expression, one eyebrow raised. Clean bold line work, generous spacing, educational composition.

For proxy-based inspection sessions, the two directions split permanently. Inbound: every packet from the client or the server still arrives at Box A's vMAC (endpoint ARP caches are unchanged) and Box A relays each one to Box B in an 0x8891 frame — this repeats per-packet for the life of the session. Outbound: Box B effectively terminates the proxy session on both sides, replying to the client and talking to the server directly from its own physical MAC. Box A relays every inbound leg and never sees a single outbound leg.

This is a genuine operational cost, not just an exam trivia point: it makes single-box packet captures unreliable, and it creates real asymmetric-path risk for anything upstream that expects symmetric flows (some stateful devices, WAN optimizers, certain routing/security appliances). This is precisely why the session outline flagged 'harder troubleshooting' and 'asymmetric path risk' as A-A's core drawbacks.

🧠
MENTAL NOTE
For proxy-inspected sessions: door IN is always Box A (every inbound packet hits the vMAC and is relayed via 0x8891), door OUT is always Box B (every reply sent directly from B's physical MAC) — repeating per-packet for the whole session. A single-box capture in A-A is not reliable evidence of failure; Box A shows only inbound halves, Box B shows the complete picture.

💭 THINK FIRST · WHEN IS IT WORTH IT

Priya wants Box B doing real work because it's sitting idle. You now know A-A only offloads proxy-based UTM sessions, that the primary always sees every packet regardless, and that A-A adds real troubleshooting cost. Time to give her the actual senior-engineer answer.

  • Does flipping to A-A meaningfully reduce Box A's CPU load — always, sometimes, or rarely? What determines the answer?
  • In a two-node cluster specifically, does the schedule setting (round-robin, ip, ipport, leastconnection...) actually do anything meaningful?
Q1 — MODEL ANSWER
It depends entirely on the traffic mix. If a meaningful share of sessions are proxy-inspected, A-A genuinely frees real CPU on Box A by handing that expensive work to Box B. If the load is mostly plain flow-based traffic, A-A offloads almost nothing — Fortinet's own guidance is explicit that A-A's goal is spending idle secondary capacity, not equalizing load; the primary will always carry more total traffic than any secondary.
Q2 — MODEL ANSWER
Almost nothing. Every schedule option (round-robin, leastconnection, ip, ipport, weight-round-robin, random) exists to answer 'which of several secondaries gets this session' — with only one possible secondary, the answer is always the same box no matter which algorithm is configured. The setting only becomes meaningful once a cluster has more than two members.
SECTION 04

When A-A Makes Sense — and When It Doesn't

A-A's value is entirely a function of how much of your traffic is proxy-inspected.

images/s3-when-it-makes-sense.png
Flat minimalistic but highly detailed cartoon illustration, warm modern colour palette, cream background, coral accents, muted gold highlights, sage greens, soft brown outlines, no gradients, no 3D. Split composition: left side shows a firewall with many coral 'proxy inspection' icons flowing to a helpful, busy Box B labelled 'worth it'; right side shows a near-identical firewall with mostly sage-green 'flow-based' icons that all stay stuck at Box A, with Box B shown idle and slightly sleepy, labelled 'limited benefit'. A small scale/balance icon sits between the two halves. Clean bold line work, generous spacing, educational composition.

A-A is not a load-balancing feature in the traffic-engineering sense — Fortinet's own material is explicit that its purpose is to spend otherwise-idle CPU and memory on the secondary, not to equalize traffic across the cluster. The primary always sees more total traffic than any secondary, because ingress (and for most session types, egress) never leaves it.

That makes the honest answer to 'should we flip to A-A' entirely traffic-mix-dependent: genuinely valuable if a meaningful share of sessions are proxy-inspected, marginal if the load is mostly plain flow-based traffic — and either way, it comes with a real operational cost in troubleshooting complexity and asymmetric-path risk that has to be weighed against the CPU gain.

🧠
MENTAL NOTE
A-A's stated goal is using idle secondary capacity, not traffic-engineering load balancing — the primary always carries more traffic than any secondary. In a two-node cluster, the schedule algorithm is functionally irrelevant since there's only one possible secondary to send a session to.
