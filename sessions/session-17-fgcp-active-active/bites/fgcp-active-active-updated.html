Active-Active Study Bite

5-minute reactivation: what gets balanced, how the handoff works, and the asymmetric-path twist.

One rule carries the whole topic: only proxy-based UTM sessions get offloaded, and once offloaded, they may never come back through the primary.

You already built this from first principles in Session 17 — this page is for fast recall, not re-teaching.

Overview Topology Exam & Checklist
💭 THINK FIRST · OVERVIEW

Quick recall before reading on.

  • What category of session gets distributed to the secondary by default?
  • Does A-A equalize traffic across both boxes?
Q1 — MODEL ANSWER
Only proxy-based UTM inspection sessions (proxy AV, DLP, explicit proxy). Flow-based and no-inspection sessions stay on the primary unless load-balance-all is enabled.
Q2 — MODEL ANSWER
No. The primary always sees every packet of every session (all ingress, and for flow-based traffic, all egress too). A-A spends the secondary's idle CPU on the expensive slice of traffic — it does not split total load evenly.
SECTION 01

Overview and Mental Model

images/s1-overview.png

Overview: Active-Active is not traffic load balancing — it's CPU offloading. The primary is the only box with a virtual MAC, so it remains the sole ingress point for every packet in every mode. What A-A adds is a per-session decision, made once at the SYN, to hand proxy-based UTM sessions to a secondary that would otherwise sit idle.

Problem it solves: in A-P, one box's CPU and memory sit almost entirely unused. A-A lets that hardware do something — specifically, the one category of work that's actually expensive (proxy-based content inspection) — without requiring the secondary to ever become a true ingress/egress point for the cluster.

🧠
MENTAL NOTE
Primary mental model: think of Box A as the front-desk clerk who takes every request. Simple requests (flow-based traffic), the clerk handles personally. Complex requests requiring a specialist (proxy-based UTM), the clerk hands to a colleague in the back office (Box B) — who then deals with the customer directly from that point on, never routing the answer back through the front desk.

💭 THINK FIRST · TOPOLOGY

Two TCP streams, same cluster, two completely different paths.

  • For Stream 1 (flow-based), which box does the client's return traffic pass through?
  • For Stream 2 (proxy-based), what MAC address does the client see in the SYN/ACK it receives?
Q1 — MODEL ANSWER
Box A, in both directions — ingress and egress. It never touches Box B.
Q2 — MODEL ANSWER
Box B's own physical MAC — not the cluster's virtual MAC. This is the asymmetric-path behavior: the SYN went to the vMAC on Box A, but the SYN/ACK arrives from a completely different physical MAC belonging to Box B.

Stream 2: a proxy-inspected session. Every INBOUND packet — from client or server — lands on Box A's vMAC and is relayed to Box B in an 0x8891 frame. Every OUTBOUND packet is sent by Box B directly. This repeats for the entire session, not just the handshake.

…Hops 5–7 repeat for every subsequent packet exchange, in both directions, for the life of the session.
The tell: compare hop 1 and hop 3. The client sends to a vMAC on Box A, but replies always arrive from a physical MAC on Box B — and this asymmetry persists per-packet for the whole session, because the endpoints' ARP caches still resolve the cluster IP to the vMAC. A capture on Box A shows every inbound half of the conversation and none of the replies.

Key terminology: vMAC — virtual MAC, owned only by the primary. 0x8891 — Ethernet type carrying forwarded session traffic between cluster members (distinct from 0x8890 hello). session-sync-dev — unrelated link used only to mirror the session table for failover, not for A-A forwarding. schedule — the config system ha parameter controlling how sessions are distributed among secondaries (irrelevant with only one secondary).

🧠
MENTAL NOTE
Stream 1 (flow-based) is a closed loop through Box A. Stream 2 (proxy-based) splits the directions permanently: the door IN is always Box A (every inbound packet hits the vMAC and is relayed to B over 0x8891), and the door OUT is always Box B (every reply comes from B's physical MAC). This repeats per-packet for the life of the session.

💭 THINK FIRST · EXAM AND CHECKLIST

Self-test — answer these cold before checking.

  • In a two-node A-A cluster, does changing config system ha schedule from round-robin to ipport change anything observable?
  • Your capture on the primary shows a SYN with no SYN/ACK for a proxy-inspected session, and the user says the connection works fine. What's your first move?
Q1 — MODEL ANSWER
No. schedule only matters when choosing between multiple secondaries. With exactly one secondary, every algorithm resolves to the same box.
Q2 — MODEL ANSWER
Capture on the secondary too — the SYN/ACK and rest of the handshake likely completed there, using Box B's own physical MAC. Don't assume a session failed based on a single-box capture in A-A.
SECTION 03

Exam Notes and Troubleshooting Checklist

images/s3-exam-and-checklist.png

Exam-critical points: (1) Only proxy-based UTM sessions are distributed by default — load-balance-all is required to force flow-based/no-inspection sessions to distribute too. (2) The forwarding traffic uses Ethernet type 0x8891, riding the heartbeat interconnect — not session-sync-dev. (3) For proxy-based sessions, every inbound packet still lands on the primary's vMAC and is relayed to the secondary via 0x8891, while the secondary sends every outbound packet directly from its own physical MAC — the asymmetry repeats per-packet, not just at the handshake. (4) schedule is functionally meaningless in a 2-node cluster. (5) A-A's stated goal is using idle secondary capacity, not equalizing traffic — the primary always sees more total traffic.

Common mistakes: confusing session-sync-dev with the A-A forwarding mechanism; assuming A-A halves the primary's load; assuming a single-box capture tells the full story of a session; assuming schedule matters regardless of cluster size; forgetting that flow-based traffic is excluded by default.

🧠
MENTAL NOTE
Troubleshooting checklist for A-A: ① Confirm which inspection type the session uses (proxy vs flow-based) — that alone tells you whether offload is even possible. ② If proxy-based and 'stuck', capture on both boxes before concluding anything is broken. ③ Check config system ha schedule and member count — don't chase a schedule change that can't do anything with one secondary. ④ If upstream devices show odd behavior on A-A sessions, suspect asymmetric-path rather than a policy issue first.
