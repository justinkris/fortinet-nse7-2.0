A Surviving Address, Never a Surviving Session

VRRP, failover timers, and why tuning the clock could never have saved those three dead sessions.

The Meridian cutover failed over in four seconds and still dropped three sessions. Both facts have answers — and they are not the same answer.

This session closes the HA phase by proving what VRRP is, and — more importantly — what it categorically is not.

Worth knowing — the "address owner" rule. Under the VRRP standard, if a router's real interface address happens to be identical to the virtual IP, that router is the "IP address owner" and is automatically assigned priority 255 — the ceiling, always outranking any configured priority. That's exactly the third-party router's situation here: 192.168.10.1 was its real gateway address long before the FortiGate showed up, so it became the address owner the moment VRRP was configured. The FortiGate, with a different real address, is a plain configured peer at priority 150.
Worth knowing — VRRP has no dedicated peer link. Unlike FGCP's dedicated heartbeat interfaces, VRRP doesn't need a special cable between the two routers at all. Advertisements are ordinary multicast frames sent onto whatever LAN segment the routers already share — in this topology, that's the shared segment behind the LAN access switch, over Gi0/1 and Gi0/2. There is no separate "VRRP link" to point at on the diagram, because there doesn't need to be one.

💭 THINK FIRST · WHY VRRP

Meridian's cutover involved an ageing third-party router and a brand-new FortiGate, running side by side for two weeks with no endpoint changes. FGCP and FGSP were both off the table. Ask yourself why before reading on.

  • Why can neither FGCP nor FGSP be used between a FortiGate and a non-Fortinet router?
  • What is the minimum two independent, mutually-distrusting boxes must share to present one gateway?
Q1 — MODEL ANSWER
FGCP and FGSP are Fortinet-proprietary — they require identical vendor, model class, and firmware, plus a private control channel. A third-party router speaks none of it. Only an open standard bridges the vendor gap.
Q2 — MODEL ANSWER
A single shared virtual gateway identity — one IP and one MAC — that each box can claim in turn. Nothing else needs to be shared, and nothing else can be, given they never exchange config.
SECTION 01

Why VRRP exists at all

VRRP — the Virtual Router Redundancy Protocol — is the lowest common denominator of high availability. It is an open IETF standard (FortiOS supports both v2 and v3), which means a FortiGate and any VRRP-compliant device can jointly back up a single gateway address. That single property is the entire reason it fit Meridian: you cannot run FGCP or FGSP between a FortiGate and a third-party router, but you can run VRRP between them.

The problem VRRP solves is narrow and specific: gateway redundancy. Endpoints on a LAN are configured with one default-gateway IP. If the single physical router owning that IP dies, every endpoint is stranded — not because the network is down, but because their one known exit no longer answers. VRRP lets a second device inherit that gateway identity transparently, so endpoints never need to know anything changed.

Frame it correctly: VRRP is not "HA lite." It solves a genuinely different problem than FGCP/FGSP. FGCP/FGSP are about keeping a Fortinet cluster alive with full state; VRRP is about keeping a gateway address reachable across any vendors. Choosing between them is a design decision, not a quality ranking.

🧠
MENTAL NOTE
VRRP is the answer to exactly one question: "how do two different-vendor boxes present one gateway?" Reach for it when — and only when — FGCP/FGSP can't run.

💭 THINK FIRST · THE VMAC TRICK

Two boxes that never exchange configuration must both answer for the exact same MAC address — and arrive at it identically without ever comparing notes. How?

  • If they can't negotiate, where does the shared virtual MAC come from?
  • What single number, known to both from their own config, could a formula turn into a MAC?
Q1 — MODEL ANSWER
It is computed, not negotiated. The vMAC is a fixed standardized prefix with one variable byte: the VRID. Formula: 00-00-5E-00-01-{VRID}.
Q2 — MODEL ANSWER
The VRID. Both boxes were configured with the same virtual router ID before either heard from the other, so both derive the identical vMAC independently.
SECTION 02

The virtual MAC is computed, not negotiated

Here is the mechanical heart of why VRRP works across vendors. The virtual MAC address is not agreed upon in any conversation — it is derived by a formula that both devices run independently:

VRRP virtual MAC formula
00-00-5E-00-01-{VRID}

Meridian uses VRID 10  ->  0x0A
Virtual MAC  =  00-00-5E-00-01-0A

The FortiGate computes 00-00-5E-00-01-0A because it is configured with VRID 10. The third-party router computes the same value for the same reason. Neither asked the other. Neither agreed to anything. There is nothing proprietary to exchange — which is precisely why a Fortinet box and a random third-party router can share one gateway. Feed them the same VRID and they will both claim the same vMAC when it is their turn to be master.

Exam hook: If an exhibit shows a MAC beginning 00-00-5E-00-01-, that is a VRRP virtual MAC, and the last byte is the VRID in hex. ...01-14 = VRID 20. Contrast with FGCP's virtual MACs, which follow a different Fortinet scheme tied to group-id and vcluster.

Analogy

Two chefs given the same recipe number, working in sealed kitchens.

  • Neither chef ever speaks to the other.
  • Both are handed the same recipe number (the VRID).
  • Both produce an identical dish (the vMAC) — because the number fully determines the outcome.
  • No coordination is needed, so it doesn't matter that the kitchens are different brands.
🧠
MENTAL NOTE
"Computed, not negotiated." The VRID → vMAC formula is the entire reason VRRP is vendor-neutral. Nothing to agree on means nothing to be incompatible about.

💭 THINK FIRST · L2 / L3 FAILOVER

When the master dies and the FortiGate takes over the same vMAC, a laptop's ARP cache already points at that vMAC. So what actually needs updating — and where?

  • Does the endpoint's ARP entry (IP → vMAC) need to change?
  • If not, why is a gratuitous ARP still required — and who is it really for?
Q1 — MODEL ANSWER
No. The endpoint still maps gateway-IP → vMAC, and that is still correct because the new master answers for the identical vMAC. Layer 3 is untouched.
Q2 — MODEL ANSWER
The switch CAM table is stale — it still forwards the vMAC toward the dead router's port. The gratuitous ARP makes every switch relearn the CAM entry and move it to the new master's port. The GARP is for the switches, not the endpoints.
SECTION 03

Failover is a Layer-2 problem, not a Layer-3 one

This is the distinction Fortinet loves to test. When the FortiGate takes over as master, two layers are in play, and only one of them actually changes:

LayerState after failoverWhy
L3 — endpoint ARPUnchanged, still validEndpoints map gateway-IP → vMAC; the new master answers for the same vMAC, so the cache is still correct.
L2 — switch CAMStale, must be correctedThe switch still forwards the vMAC out the dead master's port. Frames would be sent to a dead box.

The fix is a gratuitous ARP sent by the new master. Its purpose is widely misunderstood: it is not there to update endpoints (their L3 mapping was already right). Its real job is to make every switch on the segment relearn the CAM entry for the vMAC and move it to the FortiGate's port. Once the switches update, frames for the gateway flow to the new master, and the takeover is complete — in milliseconds.

Remember: The takeover itself is near-instant. The vMAC claim plus the gratuitous ARP take milliseconds. So if a real-world failover felt slow, the delay was not in the takeover — it was spent earlier, waiting to be allowed to act. That is the next section.

🧠
MENTAL NOTE
Endpoints never notice a VRRP failover (L3 unchanged). The gratuitous ARP exists to fix the switch CAM table (L2). Keep the two layers separate — the exam blurs them on purpose.

💭 THINK FIRST · THE TIMERS

The takeover is milliseconds, yet Marcus measured four seconds. Those seconds were spent somewhere before the FortiGate ever sent its gratuitous ARP.

  • What is the backup actually doing during those seconds?
  • How long does the protocol force it to wait before it may declare the master dead?
Q1 — MODEL ANSWER
Sitting in silence, waiting to stop hearing advertisements from the master. It cannot act until it has waited out the master-down interval.
Q2 — MODEL ANSWER
Master_Down_Interval = (3 × Advertisement_Interval) + Skew_Time. With the default 1-second advert interval, roughly 3+ seconds of silence — landing right around the observed 4.
SECTION 04

Where the four seconds went

VRRP has two timers. The advertisement interval is how often the master announces "I'm alive" (default: 1 second). The master-down interval is how long a backup waits in silence before declaring the master dead. Critically, VRRP does not use a simple "miss N hellos" rule — it uses a formula:

VRRP master-down interval
Master_Down_Interval = (3 × Advertisement_Interval) + Skew_Time

Default advert = 1s   ->   ~3s + skew  ≈  3-4 seconds

Skew_Time = ((256 − Priority) / 256) seconds
  → higher-priority backups wait slightly LESS, so they win the race

That mandated silence is exactly where Marcus's four seconds went. The FortiGate was not slow to take over — it was not permitted to conclude the master was gone until three-plus advertisement intervals of silence had elapsed. The takeover that followed was milliseconds.

The one knob to make failover faster is the advertisement interval — shrink it and master-down shrinks with it. But there is a cost, and it is the same tension that runs through all failure detection:

The flap trade-off: Too aggressive a timer misreads a transient blip — a congested LAN, a momentary CPU spike, a brief STP reconvergence — as master death. The backup seizes the vMAC unnecessarily, then the real master reasserts, and the role flaps back and forth with gratuitous-ARP storms. Fast detection versus false positives: there is no free lunch, only a setting appropriate to how stable the segment is.

🧠
MENTAL NOTE
Master_Down = (3 × advert) + skew. Default advert 1s ⇒ ~3-4s detection. The advert interval is the tuning dial — and tightening it trades detection speed for flap risk.

💭 THINK FIRST · THE DEAD SESSIONS

The path came back cleanly, yet 3 of 12 sessions died while 9 survived. This is the payoff of the whole session — and the trap the exam sets.

  • If the timer were tuned to a sub-second failover, would those 3 sessions have survived?
  • Why did exactly those 3 die while the other 9 carried on?
Q1 — MODEL ANSWER
No. Session loss is architectural, not a timing problem. VRRP synchronizes no session state, so the new master has no entry for those flows regardless of how fast it takes over.
Q2 — MODEL ANSWER
The 3 were long-lived / stateful / NAT'd flows — they arrived at the new master as out-of-state packets and were dropped. The 9 were short or stateless flows that simply built fresh sessions on the new master, unnoticed.
SECTION 05

The three dead sessions — the wrong-knob trap

Here is the sentence to carry into the exam and into production: VRRP synchronizes no session state whatsoever. Not because the peer was a third-party device — by design, even between two FortiGates. The new master inherits the IP and the MAC, and nothing else. It has never heard of the twelve flows that were running through its neighbour. No session-table entries, no NAT bindings, no tracked TCP sequence numbers.

So when a packet from an existing session lands on the new master:

  • Long-lived / stateful / NAT'd session — no matching table entry exists, the packet is treated as out-of-state, and it is dropped. The application must reconnect from scratch. These were Marcus's three casualties.
  • Short / stateless / easily re-established flow — a fresh SYN simply builds a brand-new session on the new master and nobody notices. These were the nine survivors.
The trap, stated plainly: Tuning the advertisement timer down to a sub-second failover would not have saved a single one of those three sessions. Faster failover fixes detection time, not state loss. Reaching for the timer to solve dropped sessions is the classic wrong-knob mistake.

If Vaultline needs those sessions to survive a gateway failure, VRRP is simply the wrong tool — the requirement is session synchronization, which means FGCP or FGSP. Here is how the three HA mechanisms line up on the one axis that matters:

What survives a failover?FGCPFGSPVRRP

Session state (TCP, NAT)YesYesNo — never

VRRP gives you a surviving gateway ADDRESS, never a surviving SESSION. If sessions must live through the failover, that's FGCP or FGSP — not a faster VRRP timer.
