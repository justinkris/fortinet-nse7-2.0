Session 19 · Bite · VRRP

VRRP — A Surviving Address, Never a Session

Rapid reactivation. You already understand this — this rebuilds the model in a few minutes.

⏱ 5–10 minute read
Overview

The one sentence

VRRP gives you a surviving gateway address, never a surviving session. It is the open-standard, cross-vendor HA mechanism you reach for when FGCP/FGSP cannot run. It floats one gateway identity — an IP and a MAC — between two devices. It synchronizes no session state at all, so any long-lived flow dies at failover regardless of how fast that failover is.

🧠
Anchor
Surviving ADDRESS, never a surviving SESSION. Everything else in this Bite hangs off that line.
Problem & Model

What it solves, and the mental model

Problem: endpoints have one default-gateway IP. If the single device owning it dies, they're stranded. Solution: a second device inherits that gateway identity transparently. Constraint that makes VRRP the answer: the two devices may be different vendors, so the mechanism must be an open standard — FGCP/FGSP are Fortinet-only.

Mental model: one floating gateway identity, claimed by whichever device is currently master. The identity is a computed vMAC plus the virtual IP. No state, no config, no trust travels between the two boxes — only periodic "I'm alive" advertisements.

Simplified Flow

Failover in four beats

  1. Silence: backup stops hearing the master's advertisements.
  2. Wait: it sits out the master-down interval — (3 × advert) + skew ≈ 3–4s on defaults. This is where the time goes.
  3. Claim: backup becomes master, starts answering for the same vMAC (00-00-5E-00-01-{VRID}). Milliseconds.
  4. GARP: new master sends a gratuitous ARP so the switch relearns which port the vMAC lives behind. Also milliseconds.
Key split: Beat 2 is the only slow part, and it's mandated silence, not slow machinery. Beats 3–4 are near-instant. Endpoint ARP (L3) never changes; the GARP fixes the switch CAM (L2).

Key Terminology

Terms that earn their place

  • VRID: virtual router ID; the shared number that seeds the vMAC. Same on both peers.
  • Virtual MAC: 00-00-5E-00-01-{VRID} — computed independently, never negotiated. This is why VRRP is vendor-neutral.
  • IP address owner: a router whose real interface IP equals the virtual IP; gets automatic priority 255, beating any configured priority.
  • Advertisement interval: how often the master says "I'm alive" (default 1s). The tuning dial.
  • Master-down interval: (3 × advert) + skew; the silence a backup endures before declaring the master dead.
  • Skew time: (256 − priority)/256 s; makes higher-priority backups win the takeover race.
Exam-Critical

What Fortinet tests

  • A MAC of 00-00-5E-00-01-XX is a VRRP vMAC; XX is the VRID in hex (0A=10, 14=20).
  • Master-down = (3 × advert) + skew — not "miss 3 hellos." Expect a calculation or identification item.
  • The gratuitous ARP is for the switch CAM, not endpoints. Endpoint ARP is unchanged.
  • VRRP does no session synchronization. This is the highest-value fact — it's how they trap you.
  • IP address owner ⇒ automatic priority 255.
  • FortiOS supports VRRP v2 and v3, IPv4 and IPv6, and mixed FortiGate models in one domain.
Common Mistakes

Traps & misconceptions

The trapThe correction
"Tune the timer to save the dropped sessions"Faster failover fixes detection time, not state loss. The sessions die regardless — wrong knob.
"The two routers negotiate the vMAC"It's computed from the VRID. No negotiation, no exchange.
"The GARP updates the endpoints"Endpoint ARP was already correct. The GARP updates the switch CAM table.
"VRRP is just weaker FGCP"Different problem: cross-vendor gateway float vs. Fortinet stateful cluster.
"Configured priority always wins"Not if a peer is the IP address owner — it takes automatic 255.
Troubleshooting Checklist

When VRRP misbehaves

  • Failover too slow? Check the advertisement interval; master-down is 3× it plus skew.
  • Role flapping? Advert interval too aggressive for a congested/unstable segment — back it off.
  • Wrong device is master? Check for an IP address owner (auto-255); check configured priorities and preempt.
  • Traffic blackholes briefly after failover? Switch CAM not relearning — confirm the new master is sending gratuitous ARP and the L2 path allows it.
  • Sessions dropping every failover? Expected. VRRP has no session sync. If sessions must survive, the design is wrong — needs FGCP/FGSP.
Analogy

The relay baton

Analogy
VRRP is a relay baton. FGCP/FGSP is a relay baton plus a shared memory of the race so far.
  • The baton (the gateway IP + vMAC) passes cleanly to the next runner — the crowd (endpoints) doesn't even notice the handoff.
  • But the new runner remembers nothing about the laps already run (the live sessions).
  • Anything mid-stride that depended on that memory — long-lived, stateful, NAT'd flows — falls to the ground.
  • Handing the baton faster doesn't restore the lost memory. That needs a different race entirely (stateful HA).
Self-Test

Can you reconstruct it?

A packet capture shows a source MAC of 00-00-5E-00-01-0F. What protocol, and what's the VRID?
The advertisement interval is set to 1 second. Roughly how long until a backup declares the master down, and what's the formula?
After a VRRP failover, does a client PC need to update its ARP cache? If not, what is the gratuitous ARP actually for?
A failover dropped 4 long-lived VPN sessions. An engineer proposes halving the advertisement interval. Will that save the sessions? Why or why not?
Two peers: one has a real interface IP identical to the VIP and configured priority 100; the other has priority 200. Which becomes master, and why?
