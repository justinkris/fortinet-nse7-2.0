FortiOS Architecture Overview

Why the session table is the central data structure — and how VDOMs contain the blast radius of every configuration decision.

The session entry verdict is set once at connection setup and governs everything that follows — inspection mode, offload destination, and egress path.

Understanding this single principle explains Friday's trading floor incident, the VDOM architecture decision, and will recur across HA failover, SD-WAN steering, and hardware acceleration topics throughout the course.

💭 THINK FIRST · THE SESSION TABLE

FortiOS doesn't evaluate every packet from scratch. The first packet in a connection is processed by the CPU, a decision is made, and subsequent packets follow that decision without re-evaluation. Where is that decision stored — and what does it contain?

  • When a new TCP connection arrives, what decision does FortiOS need to make — and where does it record that decision so it doesn't have to repeat it for every subsequent packet?
  • If a policy changes after a session is already established, does the existing session entry update immediately or does the change only affect new connections?
Q1 — MODEL ANSWER
FortiOS creates a session entry in the session table. That entry records the session ID, source and destination addresses, matched policy, egress interface, and — critically — the offload verdict. The NP7 uses this verdict to handle all subsequent packets without involving the CPU again.
Q2 — MODEL ANSWER
The change only affects new connections. Existing session entries retain the verdict recorded at setup time. This is why a policy change causes gradual behaviour shifts rather than an immediate cut-over — old sessions expire naturally, new sessions pick up the new policy.
SECTION 01

The Session Table — FortiOS's Central Data Structure

Every forwarding decision FortiOS makes flows from one place: the session table. When the first packet of a new connection arrives, the CPU evaluates the matching policy, determines how the connection should be handled, and creates a session entry recording that verdict. Every subsequent packet in that connection follows the recorded verdict — the CPU is not consulted again.

A complete session entry contains more than most engineers expect. It holds the session ID, source and destination addresses and ports, protocol, matched policy ID, egress interface, NAT translation details, and — most importantly — the NP7 offload verdict encoded in the npu info fields. The offload verdict is binary in effect: either the NP7 handles subsequent packets at hardware speed, or the CPU handles them in software.

Exam tip: The session table lives under diagnose sys session list — not under get. This is because the session table is raw engine state, not an operational summary. The exam distinguishes between get (clean operational output) and diagnose (raw internal engine state).

The session-entry-as-verdict model explains a real-world phenomenon that confuses many engineers: policy changes take effect gradually, not instantly. When a security profile is added to a policy, existing sessions retain their original verdict until they expire naturally. New sessions pick up the new policy immediately. In a high-frequency trading environment with short-lived connections, this produces a gradual degradation rather than a sudden cliff — exactly what Vaultline Financial observed on Friday evening.

When you see unexpected behaviour after a policy change, always check whether you're looking at old sessions still running under the previous verdict.

💭 THINK FIRST · FLOW VS PROXY

FortiOS can inspect traffic in two fundamentally different ways. One inspects packets as they pass through. The other terminates the connection entirely and creates a new one to the destination. The choice between them is made at session setup and has profound consequences for performance, session count, and NP7 eligibility.

  • If FortiOS acts as a proxy for a connection, how many session table entries exist for what the user experiences as a single connection — and where is each processed?
  • In FortiOS 7.6, does the administrator explicitly choose between flow mode and proxy mode per policy — or does something else determine which mode is used?
Q1 — MODEL ANSWER
Two session entries. One from the client to FortiGate, one from FortiGate to the server. Both run on the CPU — the NP7 is a forwarding engine and cannot terminate TCP connections, buffer streams, or reassemble application data. Proxy mode is architecturally incompatible with NP7 offloading.
Q2 — MODEL ANSWER
In FortiOS 7.6, the inspection mode is inferred from the security profiles attached to the policy. If the attached profiles require proxy-based processing, the session uses proxy mode. If all profiles are flow-compatible, flow mode is used. The administrator controls this implicitly through profile selection, not through an explicit mode toggle.
SECTION 02

Flow Mode vs Proxy Mode — Why the Split Exists

Flow-based inspection treats FortiOS as a forwarder. Packets are inspected as they transit the device — the connection remains end-to-end between client and server. The NP7 can offload the session after setup, producing hardware-speed forwarding with minimal latency. Flow mode is the default and preferred mode for performance-sensitive traffic.

Proxy-based inspection treats FortiOS as an endpoint. The client-side TCP connection terminates at FortiGate. FortiOS buffers the full application stream, performs deep content inspection, then establishes a new TCP connection to the server. This enables inspection capabilities impossible in flow mode — full SSL decryption, content reconstruction, application-level policy enforcement. The cost is significant: two CPU-bound session entries per user connection, no NP7 offloading possible, and measurably higher latency.

Critical exam point: Proxy mode is not a property of the policy — it is inferred from the security profiles attached to the policy. In FortiOS 7.6, attaching a proxy-requiring profile implicitly moves the entire session to proxy mode. The administrator who enables a profile may not realise they have also disabled NP7 offloading for every session matching that policy.

Analogy

Flow mode is a highway toll gate that scans your number plate as you pass through. Proxy mode is a customs checkpoint where you stop, get out, an inspector goes through your luggage, then you get back in a different car to continue your journey.

  • Toll gate: fast, minimal interruption, but can only see what's visible from the outside
  • Customs: slower, full inspection possible, but you were a different "connection" before and after the checkpoint
  • The NP7 can manage the toll gate automatically. It cannot perform customs inspections.
🧠
MENTAL NOTE
In proxy mode, FortiOS terminates the connection — so there are always two session table entries where the user sees one. Both are CPU-bound. This is not a configuration choice; it is an architectural constraint of what a proxy is. No setting can make a proxy session eligible for NP7 offloading.

💭 THINK FIRST · VIRTUAL DOMAINS

As an enterprise network grows — more zones, more compliance requirements, more administrative teams — a single flat FortiGate configuration becomes a liability. One routing table means one blast radius. One administrative scope means all-or-nothing access. VDOMs solve this by virtualising the firewall itself.

  • In a single flat FortiGate configuration, why can't you give a compliance officer administrative access to manage only the PCI zone without also giving them access to the trading VLAN policies?
  • What is an inter-VDOM link, what does it look like to each VDOM, and what security property does it preserve?
Q1 — MODEL ANSWER
In a flat configuration, administrative access is essentially all-or-nothing. There is one policy table, one routing table, and one configuration namespace. You cannot scope an administrator to a subset of policies. Any admin with access sees and can modify all zones.
Q2 — MODEL ANSWER
An inter-VDOM link is a virtual point-to-point connection between two VDOMs internal to the FortiGate. Each end appears to its VDOM as a regular interface — it has an IP address, participates in that VDOM's routing table, and traffic crossing it is subject to policy evaluation on both sides. This means two independent security policy checkpoints exist for inter-VDOM traffic.
SECTION 03

Virtual Domains — Isolating the Blast Radius

A Virtual Domain (VDOM) is a logically independent firewall instance running on a shared physical FortiGate. Each VDOM has its own policy table, routing table, interface assignments, and administrative scope. A change inside one VDOM cannot affect the session table, routing decisions, or policy enforcement of another VDOM. This is the architectural definition of blast radius containment.

VDOMs were not invented for complexity — they were invented to solve the operational problems that arise when a single flat configuration tries to serve multiple zones with different security requirements and different administrative teams. The compliance officer manages the PCI VDOM. Priya manages the trading VDOM. Neither can see or modify the other's configuration.

Vaultline design outcome: By placing the trading VLAN in a dedicated VDOM with only flow-based profiles, every trading session is guaranteed NP7 offloading. A proxy profile added to the corporate VDOM cannot influence the trading VDOM's session table. Friday's incident becomes architecturally impossible.

VDOMs connect to the outside world through physical interfaces assigned to them, and connect to each other through inter-VDOM links. An inter-VDOM link is a virtual point-to-point connection entirely internal to the FortiGate. Each end appears to its respective VDOM as an ordinary interface — it participates in that VDOM's routing table and is subject to that VDOM's policy enforcement. Traffic crossing an inter-VDOM link passes through two independent policy evaluation points, one in each VDOM.

🧠
MENTAL NOTE
VDOMs exist because blast radius must be bounded. Each VDOM has its own policy table, routing table, session table, and admin scope. An inter-VDOM link looks like a regular interface to each side — and policies apply to traffic crossing it, maintaining security boundaries even for internal traffic.

💭 THINK FIRST · GLOBAL SCOPE

If VDOMs are truly isolated, some configuration must exist above all VDOMs — things that belong to the physical device itself rather than to any logical instance. Knowing the boundary between global and VDOM scope is both an operational requirement and a frequently tested exam concept.

  • Name four types of configuration that must live in global scope rather than inside a VDOM — and explain why each cannot belong to a VDOM.
  • What is the management VDOM, what is its purpose, and how many can exist on a single FortiGate?
Q1 — MODEL ANSWER
VDOM creation and deletion (you cannot create a VDOM from inside a VDOM); physical interface definitions and VDOM assignment (a port exists as hardware before it is assigned to any VDOM); global administrator accounts (admins who manage multiple VDOMs must exist above all of them); firmware and licensing (these apply to the physical device, not to any logical instance).
Q2 — MODEL ANSWER
The management VDOM is the designated VDOM through which the FortiGate's own management traffic exits — FortiManager connections, FortiAnalyzer log streams, firmware updates, DNS queries. Exactly one VDOM holds this designation at any time. You designate which VDOM it is; any VDOM can be selected.
SECTION 04

Global vs VDOM Scope — Where Configuration Lives

FortiOS configuration exists in one of two scopes: global or VDOM. Global scope contains configuration that applies to the physical device itself — things that exist before any VDOM is instantiated. VDOM scope contains configuration that is specific to one logical firewall instance and has no meaning outside it.

The practical test for global scope: if the configuration cannot logically belong to any single VDOM because it affects the entire device, it lives globally. Physical interface definitions live globally because a port is hardware — it must be assigned to a VDOM, not defined by one. VDOM creation lives globally because you cannot bootstrap a VDOM from inside a VDOM. Global administrator accounts live globally because multi-VDOM admins must have a scope that transcends any individual VDOM.

Management VDOM: One designated VDOM handles all of the FortiGate's own management traffic — FortiManager connectivity, FortiAnalyzer log forwarding, firmware updates, NTP, DNS. Only one management VDOM can be active at any time. Any VDOM can be designated. This ensures management plane traffic follows a predictable, controlled routing path separate from user data traffic.
🧠
MENTAL NOTE
Global scope = the physical device. VDOM scope = one logical firewall instance. If you can ask "which VDOM does this belong to?" and the question doesn't make sense, it's global. If the configuration only has meaning within one logical firewall context, it's VDOM-scoped. The management VDOM is exactly one — and any VDOM can hold that role.

💭 THINK FIRST · TROUBLESHOOTING

Priya sees offload=0/0 in a trading VDOM session entry despite having no proxy profiles on any policy. Before reaching for additional commands, a systematic engineer reads the evidence already in the session entry. The no_ofld_reason field tells you which category of problem you're dealing with before you run a single additional command.

  • You see offload=0/0 with no_ofld_reason: helper in a trading VDOM session. Is this a problem requiring investigation, or expected behaviour — and how do you decide?
  • What four conditions can produce offload=0/0 in a session entry, and which of these cannot be resolved through configuration changes?
Q1 — MODEL ANSWER
Expected behaviour — if you confirm the protocol genuinely requires a session helper (FTP, SIP, H.323, etc.). Identify the protocol, confirm a helper is appropriate for it, and move on. Do not chase helper reason codes unless you suspect the wrong protocol is triggering a helper, or a helper is assigned to a protocol that doesn't need one.
Q2 — MODEL ANSWER
The four conditions: (1) proxy-based security profile attached — a configuration decision, reversible; (2) session helper required — an architectural constraint, cannot be configured away; (3) software tunnel interface — an architectural constraint for GRE/SSL VPN tunnels; (4) auto-asic-offload explicitly disabled on the policy — a configuration decision, reversible. Constraints 2 and 3 cannot be resolved by changing configuration.
SECTION 05

Troubleshooting Session Offload in a VDOM Environment

When a trading VDOM session shows offload=0/0 despite clean flow-based policies, the no_ofld_reason field in the session entry is your first diagnostic tool. Read it before running any additional commands. It immediately categorises the problem as either an architectural constraint (cannot be fixed by configuration) or a configuration decision (can be reversed).

no_ofld_reason ValueCategoryCorrect Response
helperArchitectural constraintIdentify protocol, confirm helper is appropriate, accept and move on
software-tunnelArchitectural constraintConfirm interface type; GRE/SSL VPN cannot be offloaded — expected
ofld-disabledConfiguration decisionCheck auto-asic-offload on the matching policy; enable if appropriate
proxy (or profile-based)Configuration decisionIdentify which attached profile forces proxy mode; evaluate whether it belongs on this policy
rsvdOften short-lived sessionCheck session duration; if very short, offload evaluation may not have completed — usually benign

The investigation sequence when offload=0/0 appears unexpectedly in a trading VDOM:

  1. Read no_ofld_reason — categorise as constraint vs decision before doing anything else
  2. Check session duration — is this a very short-lived session that expired before offload completed?
  3. Identify the protocol — does it match a known session helper protocol (FTP, SIP, H.323)?
  4. Check the ingress interface — is it a software tunnel (GRE, SSL VPN)?
  5. Check the policy — is auto-asic-offload disabled?
  6. Review attached profiles — is any profile implicitly forcing proxy mode?
Exam trap: Questions that include the phrase "regardless of policy configuration" are pointing you toward architectural constraints — session helpers and software tunnels. These cannot be resolved by any policy change. Questions about configuration decisions will include words like "disabled" or "profile" as clues.
🧠
MENTAL NOTE
Read no_ofld_reason before reaching for any other command. It costs nothing and immediately tells you whether you're dealing with a constraint (accept it) or a decision (investigate and potentially reverse it). The constraint vs decision framework is the single most valuable instinct in session offload troubleshooting.
