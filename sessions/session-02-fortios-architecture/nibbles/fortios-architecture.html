The Session Verdict Model

One decision. Set once. Governs everything. — Under 2 minutes.

What Happens When a Connection Arrives
1
Packet 1
First packet of new connection
2
CPU Evaluates
Policy match, profile type, route lookup
⚡
Verdict Written
Session entry created, offload decision recorded
4
Packets 2–N
Follow the recorded verdict. CPU not consulted.

The verdict is permanent for the session's lifetime. Policy changes only affect new connections.

Flow Mode
1 Session
Pass-through. NP7 eligible. Low CPU. Near wire-speed after offload.
Proxy Mode
2 Sessions
Connection terminated. Both entries CPU-bound. NP7 architecturally impossible.
The Rules That Matter
1
Mode is inferred, not configured. FortiOS 7.6 reads the attached security profiles and infers flow or proxy. The engineer controls mode through profile selection — whether they know it or not.
2
Proxy is all-or-nothing per session. One proxy-requiring profile forces the entire session into proxy mode — both session entries, both directions, both on the CPU.
3
VDOMs isolate the verdict space. Each VDOM has its own session table and policy table. A proxy profile in VDOM A cannot change the offload verdict of sessions in VDOM B.
🎯
Exam Trigger Phrases
"regardless of policy configuration" → architectural constraint (session helper or software tunnel) — cannot be fixed by config changes.

"all sessions on the policy" + proxy profile → remember: the verdict affects all sessions, not just new packets.

"management VDOM" → exactly one. Any VDOM can hold the role. One at a time.
