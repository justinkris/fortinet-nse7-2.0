Study Guide · NSE7 EF 7.6 · Domain 4 — Routing

Locks, Silence, and the Lie of Omission

OSPF authentication, stub & totally stubby areas, area range, summary-address, and passive interfaces — Session 22 at Vaultline Financial.

Hello-only OSPF works in a lab. Production OSPF must decide who gets to speak and how much each router needs to be told.

These five features are the ones the exam most often hides inside a "why is this not working?" scenario — because each one changes behavior silently, at a boundary you can't see from where you're standing.

💭 THINK FIRST · AUTHENTICATION

Daniel's rogue laptop formed a full adjacency with someone's production core. Before reaching for a feature, ask what was ever standing in its way.

  • Of the things two OSPF routers must match to become neighbors — area ID, subnet, timers, MTU — which are actually secret from a device plugged into the same VLAN?
  • Why does a plaintext password fail against exactly the attacker it's meant to stop, and what does MD5/HMAC change about what crosses the wire?
Q1 — MODEL ANSWER
None of them. Area ID and hello/dead timers are broadcast in cleartext in every hello, every 10 seconds, to 224.0.0.5. The subnet must be matched just to have a working interface on the VLAN. MTU isn't even checked at the hello stage — it lives in DBD packets during Exchange (that's why an MTU mismatch shows as stuck ExStart, not a missing neighbor). Default OSPF runs on pure trust: matching the published fields IS the trust.
Q2 — MODEL ANSWER
Type 1 puts the password itself, in cleartext, inside the hello — the same capture that reveals the area ID reveals the password. Type 2 never transmits the key: it sends a digest of (key + packet contents), so an attacker with a full capture archive still cannot compute a valid digest without the key. A rolling sequence number is hashed in, so captured packets can't be replayed later either.
SECTION 02

Authentication — OSPF Runs on Pure Trust

The finding that opened the session: there is no secret handshake in default OSPF. Every field two routers must match to become neighbors is either broadcast in plaintext or trivially satisfied by being on the wire:

FieldHow a rogue device gets itWhen it's checked
Area IDPlaintext field in every hello (every 10s to 224.0.0.5)Hello
Subnet / maskMust already be configured just to be on the VLAN — nothing to "discover"Hello
Hello / dead timersPlaintext fields in every helloHello
MTUSet a normal MTU — done. Not in the hello at allDBD / Exchange (mismatch = stuck ExStart)
Correction from this session: MTU is not carried in the hello. It's announced in Database Description packets during Exchange. Your own S21 rule was the proof: if MTU were a hello gate, a mismatch could never produce a stuck ExStart — the routers would never have gotten past hello.

Passive interface can't save the interface that matters, either: the core trunk carries real neighbors, and passive kills hellos for everyone — rogue and legitimate alike. The only defense that works on an interface that must actively peer is to add something to the exchange that a wire-listener can't observe: a shared secret — the same shape of mechanism as the FGCP heartbeat and VRRP group secrets.

The three authentication types

TypeMechanismSurvives a tcpdump?Actual protection
Type 0 — NoneMatch the plaintext fields, you're in—None. Pure trust (the FortiOS default)
Type 1 — PlaintextPassword sent in cleartext inside the packetNo — one capture reveals itFat-finger protection only (uncoordinated admins)
Type 2 — Cryptographic (MD5 / HMAC-SHA)Digest of (key + packet) sent; key never transmittedYes — capture archive is useless without the keyReal: only key-holders form adjacencies

Two properties complete the Type 2 story. Anti-replay: a non-decreasing sequence number is part of what gets hashed, so replaying a captured hello later fails — the sequence is stale. Scope: authentication is per-interface, not global. That's what makes it usable: HMAC on the exposed trunk, nothing (or a different key) on the locked-comms-room point-to-point link. A mismatch between two ends of a link — one side authed, the other not, or different keys — fails exactly like an area-ID mismatch: no neighbor entry ever appears. Invisible neighbor, not a stuck state.

FortiOS CLI — per-interface OSPF authentication
config router ospf
    config ospf-interface
        edit "core-trunk"
            set interface "port3"
            set authentication md5        <- or: text (Type 1) / none (Type 0)
            config md5-keys
                edit 1
                    set key-string <shared-secret>
                next
            end
        next
    end
end
Exam trap: the tested distinction is Type 1 vs Type 2, not which hash algorithm. The distractor answer is plaintext auth "protecting" against a sniffing attacker — it doesn't; capture defeats it. And remember the failure signature: auth mismatch = no neighbor at all, which means a visible neighbor at any state has already exonerated authentication (your S21 elimination trick still holds).
🧠
MENTAL NOTE
Type 0 trusts everyone. Type 1 trusts anyone who owns a packet sniffer. Type 2 trusts only key-holders — because the key never crosses the wire, only a digest that's worthless without it.

💭 THINK FIRST · AREA TYPES

The DR-site router has one exit and dozens of Type 3/5 entries it will never act on differently. You derived the fix from first principles this session — reconstruct the chain.

  • Why must stub be configured on every router in the area, and what mechanism enforces the agreement at hello time?
  • Why is "totally stubby" a unilateral ABR-side decision needing no new handshake bit — what's different about suppressing Type 3s vs banning Type 5s?
Q1 — MODEL ANSWER
The E-bit in the hello's Options field. Set = "I accept external (Type 5) routes"; a stub router clears it. Mismatched E-bits fail at hello, same family as an area-ID mismatch: no adjacency ever forms. That's a design virtue — a stub router receiving a Type 5 its area isn't supposed to carry is a protocol violation, so OSPF refuses the relationship up front rather than tolerating silent disagreement about what belongs in the area.
Q2 — MODEL ANSWER
Suppressing Type 3s is a quantity change, not a type change. A router receiving one default Type 3 instead of fifty specifics processes it normally — nothing breaks, so nothing needs negotiating. Receiving an unexpected LSA *type* (a Type 5 in a stub area) is a real violation, which is why only that gets an up-front hello check. "Totally" is purely an origination decision the ABR makes alone: originate one default Type 3, stop sending the rest.
SECTION 03

Area Types — How Much Does a Leaf Need to Be Told?

The derivation ran in this order, and it's worth preserving because the exam tests the reasoning, not the labels. The DR-site router has exactly one exit. Every Type 3 and Type 5 in its database resolves to the same decision: "send it toward HQ." The information floor for that decision is a single default route. Everything above the floor costs LSDB memory and — the live, ongoing tax — a partial SPF run every time any of those prefixes changes anywhere in the domain, for a router whose next hop can never change.

Stub collapses the external half: no Type 5s enter the area; the ABR injects a default in their place. Crucially, stub is not a local knob — a router that unilaterally ignored Type 3/5s would still receive, store, and SPF them; the flooding has to stop at the source (the ABR), and every router in the area must agree, enforced by the E-bit handshake at hello time. Totally stubby then collapses the inter-area half too — the ABR replaces the individual Type 3s with a single default Type 3 — and this half is unilateral, because fewer LSAs of a known type breaks nothing.

Area typeType 5 (external)Type 3 (inter-area)Local ASBR allowed?Handshake
Regular (default)Yes, full detailYes, full detailYesE-bit set
StubNo → default from ABRYes, full detailNo — absoluteE-bit cleared, must match area-wide
Totally stubbyNo → defaultNo → defaultNoE-bit only; "totally" is ABR-side, unilateral
NSSANo Type 5s in, but local ASBR originates Type 7 → ABR converts to Type 5 for the rest of the domainYes, full detailYes (via Type 7)N-bit variant of the same idea
Totally NSSAAs NSSANo → defaultYes (via Type 7)As NSSA; inter-area suppression ABR-side

NSSA exists for one reason: a plain stub area's Type 5 ban is absolute — it cannot host an ASBR at all. If the leaf site itself needs to redistribute something local (a static route, a small legacy RIP segment), NSSA relaxes the ban with Type 7: an external LSA that lives only inside the NSSA, which the area's ABR translates into a genuine Type 5 for everyone else. The DR site as it stands is a pure "everything through HQ" leaf with no local route sources — so totally stubby, not NSSA, is the right call.

FortiOS CLI — area types (ABR shown; stub type must match area-wide)
config router ospf
    config area
        edit 0.0.0.3
            set type stub
            set stub-type no-summary     <- ABR only: makes it TOTALLY stubby
        next                                (summary = plain stub)
        edit 0.0.0.2
            set type nssa                <- if a leaf needs a local ASBR
        next
    end
end
Exam traps: (1) "Configure stub on the ABR only" — wrong; the E-bit mismatch means the ABR and internal routers never become neighbors. The symptom is a missing neighbor, not missing routes. (2) "A stub area can have an ASBR if you're careful" — never; that's what NSSA is for. (3) The backbone (area 0) can never be stub of any flavor.
🧠
MENTAL NOTE
Banning a Type needs a handshake (E-bit — mismatch means no neighbor). Sending fewer of a Type needs none ("totally" = ABR alone). Needing a local ASBR anyway = NSSA, smuggled as Type 7, converted to Type 5 at the border.

💭 THINK FIRST · SUMMARIZATION

Priya wants Harbourview visible for monitoring — no black-box default. There's a middle ground between "flood every /24" and "flood nothing but a default."

  • If 10.50.9.0/24 — one of the four /24s inside the 10.50.8.0/22 range — flaps, what happens to the summary Type 3 in area 0?
  • area range and summary-address both summarize. What's the difference in who runs them and which LSA type they act on?
Q1 — MODEL ANSWER
Nothing. The summary is the ABR claiming "traffic for this block comes through me" — not "all four subnets exist." It stays advertised, unchanged, as long as at least one component subnet remains reachable through that ABR. That's the payoff: one flapping /24 no longer means one flapping LSA reaching every backbone router. Volatility is hidden behind a stable boundary.
Q2 — MODEL ANSWER
area range: run on the ABR, summarizes Type 3s crossing between areas. summary-address: run on the ASBR, summarizes Type 5s before externals ever hit the backbone — relevant the moment FG-EDGE-P starts redistributing chunky external blocks. Same idea (shorter mask covering multiple prefixes), different border, different LSA type.
SECTION 04

Summarization — Hiding Volatility Behind a Stable Boundary

You produced the definition cold this session: advertise a prefix with a shorter mask so it covers multiple subnets. At Harbourview's ABR, area range takes the four contiguous /24s (10.50.8.0 – 10.50.11.0) and originates one Type 3 for 10.50.8.0/22 instead of four. The area stays visible — unlike totally stubby's black-box default — but the backbone sees one stable claim instead of four flap-prone ones.

The critical behavior: the summary is the ABR's claim that "traffic for this block comes through me" — not an inventory of live subnets. A component /24 can flap, or die entirely, and the summary in area 0 does not move as long as at least one member remains reachable. This is the same trade as stub-ness, made once at a border instead of area-wide: visibility traded for stability. Type 3 summarization is the ABR's tool; the ASBR gets the identical trick for externals via summary-address, compressing Type 5s before they fly domain-wide — which becomes real for FG-EDGE-P the moment redistribution lands (S23).

FortiOS CLI — both summarization points
config router ospf
    config area
        edit 0.0.0.2
            config range                  <- ABR: inter-area (Type 3)
                edit 1
                    set prefix 10.50.8.0 255.255.252.0
                next
            end
        next
    end
    config summary-address                <- ASBR: external (Type 5)
        edit 1
            set prefix <block> <mask>
        next
    end
end

The troubleshooting consequence — the lie of omission

Two weeks after go-live: "Harbourview can't reach 10.50.9.0/24." You check the ABR — the /22 summary is still advertised into area 0, perfectly healthy. That tells you nothing about 10.50.9.0/24 specifically. The summary survives on one living member. The specifics still exist in full detail — but only inside area 0.0.0.2, because summarization happens exclusively at the boundary crossing. So the diagnosis moves inside: get router info ospf database on a router in area 2, or its routing table, shows the genuine per-prefix truth the border is hiding.

Remember: summarization and stub-ness both trade visibility for stability — and the cost of the trade is that troubleshooting must happen closer to the source, not at the boundary. Know where the lie of omission lives in your own design.
🧠
MENTAL NOTE
A summary is a claim about a block, not an inventory of subnets. It stays up while one member lives — so a healthy summary at the border proves nothing about any specific prefix. Diagnose inside the area.

💭 THINK FIRST · PASSIVE & GO-LIVE

"Quiet but still in the database" — the session-goal phrase for passive interfaces. It's precisely the distinction the exam tests.

  • An interface is made passive. Does its subnet vanish from OSPF, or is something still advertised — and if so, what and by whom?
  • Why is passive the right tool for the office VLAN but useless for the core trunk in Daniel's scenario?
Q1 — MODEL ANSWER
Still advertised. Passive stops the hello process — no hellos out, no adjacency possible — but the router's own Type 1 LSA still lists the subnet as a stub network entry ("I have this link, cost X, no neighbor on it"). The network stays fully reachable area-wide; the router just refuses to peer on that wire. Passive hides the willingness to peer, not the network.
Q2 — MODEL ANSWER
The office VLAN has no legitimate neighbors — silencing hellos costs nothing and removes the rogue-adjacency surface entirely. The core trunk carries real neighbors — passive would kill them along with the rogue. On interfaces that must peer, the only defense is authentication; passive and auth are complementary tools for two different interface roles.
SECTION 05

Passive Interfaces & the Go-Live Design

A passive interface originates no hellos, so no adjacency can ever form on it — but the router still puts the subnet into its own Type 1 LSA as a stub network entry. The route is known and reachable everywhere in the area. "Quiet but still in the database" is exactly right: the exam's trap phrasing is "if I make an interface passive, does that subnet disappear from OSPF?" — and the answer is no.

All five features on one map — go-live day

  • Office VLAN (FGT-HQ-CORE): passive — no OSPF spoken, subnet still routed. Daniel's conference-room jack is dead air to a rogue OSPF daemon.
  • Core switch trunk: HMAC-SHA authentication — real neighbors keep peering; matching the plaintext fields no longer buys a rogue device anything.
  • Area 0.0.0.3 (DR site): totally stubby — set type stub everywhere in the area (E-bit handshake), no-summary on the ABR. Dozens of Type 3/5s become one default.
  • Area 0.0.0.2 (Harbourview): regular area + area range 10.50.8.0/22 — visible for monitoring, stable at the border.
  • FG-EDGE-P (next session): summary-address queued for the moment redistribution makes its ASBR badge real.

The elimination trick, upgraded: S21 taught that a visible neighbor at any state exonerates timers/area/subnet. Session 22 adds two more to the exonerated list — authentication and the E-bit — because both are hello-stage gates. A visible neighbor means every hello-stage field already matches.
