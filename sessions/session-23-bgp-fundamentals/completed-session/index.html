Study Guide · NSE7 EF 7.6 · Session 23

Two ISPs, One Prefix, One Ordered List

BGP doesn’t calculate a winner — it walks a ladder of attributes until one of them finally disagrees.

Administrative Distance picks a protocol to trust. Best-path selection picks between two speakers of the same protocol — and that’s a fight AD was never built to referee.

Vaultline Financial — FG-EDGE-P now dual-homed to ISP-A and ISP-B. Same prefix, two eBGP neighbors, one decision to make.

Why a List The Ladder In vs Out AS & Loops eBGP TTL
💭 THINK FIRST · WHY A LIST

FG-EDGE-P has two eBGP neighbors, ISP-A and ISP-B, both advertising the same prefix. You already know Administrative Distance cold — Static 10, eBGP 20, OSPF 110, iBGP 200. So why doesn't it help here?

  • Both candidate routes are eBGP. What does AD actually compare, and why does that make it silent on this specific fight?
  • OSPF settles every tie with one calculated number (cost). Why would BGP need an entire ordered list of attributes instead of a single metric?
Q1 — MODEL ANSWER
AD compares different routing sources — it's how a router decides whether to trust a static route, an eBGP route, or an OSPF route more, when they disagree about the same destination. Both ISP-A and ISP-B routes are eBGP, so they carry the identical AD value (20 = 20). AD has already done its job by the time you're comparing two eBGP peers — there's no tie left for it to break.
Q2 — MODEL ANSWER
OSPF's cost is an objective, physical fact — bandwidth — and every router in the same administrative domain agrees on the same formula to calculate it. ISP-A and ISP-B are separate companies with separate infrastructure, separate pricing, and no shared formula. "Which path is better" is a policy question, not a physics question — so BGP needs a mechanism for humans to express preference, tie-broken in a strict, predictable order when preferences are silent.
SECTION 01

A Policy Protocol, Not a Topology Protocol

Every routing protocol you've studied so far — OSPF included — answers "which path is shortest?" with a number derived from something physically true: bandwidth, hop count, delay. Two routers running the same protocol, looking at the same link, will always calculate the same cost, because the formula is shared and the inputs are technical facts nobody can argue with.

BGP breaks that assumption completely. FG-EDGE-P's two candidate routes — one from ISP-A, one from ISP-B — aren't being compared on a shared formula. They're two independent companies' opinions about how to reach the same destination, and neither company's infrastructure numbers mean anything to the other. There is no "BGP cost" the way there's an "OSPF cost," because there's no shared physical truth to measure. What's left is policy — Vaultline's own preference, expressed through a strict, ordered list of attributes that BGP checks one at a time, stopping at the very first one that actually differs.

SourceAdministrative Distance (FortiGate)What it encodes
Static10Human said so, directly
eBGP20Direct claim from outside the AS — closest to the original source
OSPF110Internal topology fact, computed
iBGP200A route someone else in your own AS already validated
Exam tip: AD resolves conflicts between different protocols offering the same prefix. It never resolves a conflict between two neighbors of the same protocol — that's what the BGP best-path algorithm exists for. Seeing "eBGP vs eBGP" in a question is your cue to reach for the best-path order, not the AD ladder.
🧠
MENTAL NOTE
AD picks a protocol to trust. Best-path picks between two speakers of the same protocol — because unlike OSPF's shared cost formula, no formula is shared between two competing ISPs. That gap is filled with an ordered list of policy attributes, not a calculation.

💭 THINK FIRST · THE LADDER

Weight sits at the very top of the best-path order — checked before anything else, including Local Preference.

  • Why would BGP put the most private, least-shared attribute first, instead of the one that represents the whole AS's opinion?
  • If Weight and Local Preference both tie, what gets checked next — and is it something Vaultline configures, or something that arrives on the route already built?
Q1 — MODEL ANSWER
Order in the ladder isn't about importance — it's about scope of authority. Weight is checked first specifically because it's the most local: a single router's ability to override everything else, including its own AS's stated policy, without asking permission from anyone. Checking it first guarantees that a per-router override always wins if one is set.
Q2 — MODEL ANSWER
AS-Path is next, and it's not something Vaultline configures at all — it arrives on the route already built, growing by one ASN every time the route crosses into a new autonomous system on its way here.
SECTION 02

The Full Order, Top to Bottom

BGP walks this list in strict order and stops at the first attribute that actually differs. Everything below that point is never even consulted — a "better" MED further down the list cannot rescue a route that already lost on AS-Path.

#AttributeScopeWins when
1WeightLocal to the router — never advertised, not even to iBGPHighest
2Local PreferenceiBGP only — stripped at the eBGP boundaryHighest
3Locally originated—Self-originated beats learned
4AS-Path lengthCrosses eBGP, grows every hopShortest
5Origin typeCrosses eBGPIGP < EGP < Incomplete
6MEDCrosses one eBGP boundary, compared per-neighbor-ASLowest
7eBGP over iBGP—eBGP-learned wins
8Lowest IGP metric to next-hop—Lowest
9Oldest eBGP route—Oldest (stability)
10Lowest Router ID—Lowest
11Lowest Neighbor IP—Lowest — final tie-break
Common misconception: AS-Path length is not a performance metric. It counts organizational boundaries crossed, not physical distance, latency, or bandwidth. A 2-hop AS-Path through two congested networks beats a 4-hop AS-Path through four lightly-loaded ones, every time — BGP doesn't know or care about the difference.
Exam tip: MED is compared only between routes learned from the same neighboring AS by default (unless a policy explicitly changes that). It's never used to compare a route from ISP-A against a completely unrelated route from ISP-B.

Worked example — the exact FG-EDGE-P scenario: Weight ties (0=0), Local Preference ties (100=100 default), so BGP moves to AS-Path. ISP-A offers 65010 65020 (2 hops); ISP-B offers 65030 (1 hop). ISP-B wins on AS-Path — and MED is never even read, regardless of what its numbers say.

🧠
MENTAL NOTE
BGP stops at the first attribute that differs. A table with a favorable MED further down is a distractor if AS-Path already broke the tie above it — always check the ladder top-down, never jump to a metric you find compelling.

💭 THINK FIRST · IN VS OUT

Priya says: "I want ISP-A preferred, always." That's easy for traffic leaving Vaultline. It's a completely different problem for traffic arriving from the internet.

  • Which router's BGP process decides which link FG-EDGE-P's own outbound traffic uses? Which router decides which link a stranger's inbound traffic arrives on?
  • If you can't configure a knob on someone else's router, what's the only lever left to influence their decision?
Q1 — MODEL ANSWER
Outbound: FG-EDGE-P's own BGP process picks a winner between the routes it received from ISP-A and ISP-B — Vaultline's own hardware, Vaultline's own decision. Inbound: the sender's own network runs its own best-path process, against routes it received. FG-EDGE-P has zero authority over that calculation.
Q2 — MODEL ANSWER
You can only shape what you advertise outbound toward that other AS, and hope its policy responds the way you want — a proxy signal, not a command.
SECTION 03

Steering Your Own Traffic vs. Requesting Someone Else's

This is the idea that ties the whole session together. Every attribute in the ladder falls into one of two completely different jobs, and confusing them is one of the most common real-world (and exam) mistakes in BGP.

JobAttribute(s)Who actually decidesGuaranteed?
Steer your own outbound trafficWeight, Local PreferenceYour own router / your own ASYes — it's your hardware
Request influence over inbound trafficAS-Path prepending, MEDThe neighboring AS's own policyNo — they can ignore it

Local Preference and Weight work because they act on routes FG-EDGE-P already received — comparing ISP-A's offer against ISP-B's offer decides which link Vaultline's own packets leave through. That comparison happens entirely on hardware Vaultline owns.

Inbound traffic is a different problem entirely. A customer reaching Vaultline's public app has their own router running its own best-path math, over routes it received from its own upstreams. FG-EDGE-P can't configure anything on that router. The only lever left is what Vaultline advertises outbound — AS-Path prepending artificially lengthens the path Vaultline sends toward ISP-B, hoping every external network's own math naturally prefers entering via ISP-A instead. MED goes one step further: an explicit number sent toward a neighboring AS, saying "prefer my lower-numbered entrance" — but only if that AS's engineers configured their policy to actually honor it.

Analogy

AS-Path is a law everyone obeys. MED is a polite request someone can ignore.

  • Every AS on the internet must count AS-Path length — it's baked into every router's algorithm, no exceptions, no cooperation required.
  • MED only works if the receiving AS's engineer specifically configured their policy to look at it and respect it.
  • That's why MED sits so low in the order (#6) — it's the first attribute in the whole list that only functions if the other side agrees to play along.

💭 THINK FIRST · AS & LOOPS

FG-EDGE-P and FG-EDGE-DR both belong to Vaultline. ISP-A and ISP-B are two unrelated companies.

  • Should FG-EDGE-P and FG-EDGE-DR carry the same ASN, or different ones — and why?
  • What does a BGP router do the instant it sees its own ASN already sitting somewhere in a received AS-Path?
Q1 — MODEL ANSWER
Same ASN — one company, one routing policy, one AS. ISP-A and ISP-B are totally independent companies and carry totally independent ASNs.
Q2 — MODEL ANSWER
It silently drops the route. If its own ASN is already in the AS-Path, accepting the route would mean creating a loop back through itself — so it refuses on sight.
SECTION 04

What an ASN Actually Is

An Autonomous System Number identifies one routing domain under one administrative policy — not a device, not a link, a whole organization's worth of routers acting under one set of decisions. That's exactly why FG-EDGE-P and FG-EDGE-DR share a single ASN: they're both Vaultline, both meant to enforce the same policy (as we just built with Local Preference), and iBGP's whole design assumes "same ASN" means "trusted, same-organization neighbor." ISP-A and ISP-B, as separate companies, carry entirely independent ASNs with no relationship to Vaultline's or each other's.

Unlike an OSPF Area ID — a label Vaultline invents purely for its own internal use, meaningless outside its own network, freely reusable without any risk of collision with anyone else's OSPF domain — an ASN has to be globally unique. It's registered through IANA and the regional internet registries, the same authority structure that hands out public IP address blocks. Two unrelated companies quietly reusing the same ASN isn't an administrative inconvenience; it actively breaks BGP's own defense mechanism.

That mechanism is AS-Path loop prevention: when a BGP router receives an advertisement, it checks whether its own ASN already appears anywhere in that route's AS-Path. If it does, the route is silently dropped — accepting it would mean routing back through a network segment the packet has (as far as BGP can tell) already crossed. This is BGP's structural answer to the same problem OSPF solves by having every router compute Dijkstra over an identical database: don't create a loop, ever, by construction.

Common misconception: Duplicate ASNs only cause a problem if the two companies advertise overlapping prefixes. Not true — even with completely disjoint prefixes, the moment a legitimate route from Company X's AS 65010 transits anywhere near Company Y's AS 65010, the loop-prevention check mistakes coincidence for an actual loop and silently drops otherwise-valid, unrelated traffic.
🧠
MENTAL NOTE
ASN uniqueness isn't administrative tidiness — it's the load-bearing assumption behind BGP's entire loop-prevention mechanism. An Area ID is local and freely reusable; an ASN is global and registered, because BGP actively checks for it in every AS-Path it receives.

💭 THINK FIRST · eBGP TTL

BGP rides on TCP, and TCP packets carry a TTL that decrements at every router hop.

  • What TTL does FortiGate set by default on an eBGP session, and what real-world topology does that value assume about where ISP-A's router physically sits?
  • If that assumption doesn't hold, what symptom would you actually see on FG-EDGE-P — an error message, or silence?
Q1 — MODEL ANSWER
TTL = 1. It assumes a direct physical cross-connect — same rack or meet-me-room, one cable, zero intermediate routers between FG-EDGE-P and ISP-A's router.
Q2 — MODEL ANSWER
Silence. The TCP SYN gets discarded by an intermediate hop before it ever reaches the far router — no TCP handshake completes, no error message, just a neighbor that never appears.
SECTION 05

eBGP Assumes You're Right Next Door

BGP sessions ride on ordinary TCP (port 179), and every TCP packet carries a TTL that decrements once per router hop, getting silently discarded if it ever reaches zero. FortiGate's default eBGP TTL is 1 — meaning the very first TCP SYN toward a new eBGP neighbor is only willing to survive exactly one hop.

That default isn't arbitrary; it encodes an assumption about physical topology. A classic enterprise-to-ISP handoff genuinely is one hop — a direct cross-connect, same rack or same meet-me-room, one cable between FG-EDGE-P's WAN interface and ISP-A's router. TTL=1 works without anyone touching it because the real-world topology matches the assumption.

But some legitimate eBGP scenarios genuinely aren't directly adjacent — peering across a routed WAN, or via a route-server that sits more than one hop away. In those cases, TTL=1 doesn't produce an error; it produces silence. The TCP SYN is discarded by an intermediate router before the session ever begins, and FG-EDGE-P simply never sees a neighbor appear — no diagnostic message pointing at the cause.

Troubleshooting pattern: A BGP neighbor that never comes up, with no error logged, is the same failure family as OSPF's hello-gate mismatches from Session 22 (area ID, subnet, auth, E-bit) — a silent, structural refusal rather than a stuck intermediate state. For BGP specifically, check reachability and actual hop count before assuming a config typo.

The fix is FortiOS's ebgp-multihop setting — it deliberately raises the TTL FG-EDGE-P will accept from a specific neighbor, for the legitimate cases where the peer genuinely isn't directly connected. This is a conceptual flag for now; the full config router bgp skeleton — including this and the actual timer values — is next session's opening material.

🧠
MENTAL NOTE
eBGP defaults to TTL=1 because the assumed topology is a direct cross-connect. Break that assumption without adjusting the TTL, and the symptom isn't an error — it's a neighbor that simply never appears.
