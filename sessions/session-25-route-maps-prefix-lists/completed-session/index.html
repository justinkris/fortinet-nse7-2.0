Study Guide · NSE7 EF 7.6 · Session 25

Learn Everything, Keep Only What You Choose

BGP's default posture is "trust and propagate everything." Route-maps and their matchers are how production routing says no.

Almost every BGP exam scenario hides a route-map line. Reading them fluently is the difference between a 5-minute question and a wrong answer.

Priya found an ISP-A peering route on FG-EDGE-DR that should never have arrived there. This session builds the three matching tools — prefix-lists, AS-path ACLs, community-lists — and the route-map machine they plug into.

Prefix Lists AS-Path & Communities Route-Map Anatomy
💭 THINK FIRST · PREFIX LISTS

FG-EDGE-P peers with ISP-A over eBGP with zero filters configured. ISP-A sends its full internet table. Before any tool can fix this, you need to know exactly what the unfiltered default behavior is — because that default is the problem the whole session solves.

  • With no filtering at all, does FG-EDGE-P accept everything ISP-A sends — and does it then re-advertise all of it onward to its iBGP peer FG-EDGE-DR?
  • The entry 198.51.100.0/24 le 26 — does it match the bare /24 itself? Does it match 198.51.100.192/27?
Q1 — MODEL ANSWER
Yes to both. BGP's default is to accept everything a peer sends into the BGP table, and because those routes are eBGP-learned (not iBGP-learned), split-horizon does not block them — they flow onward to iBGP peers via the route reflector. No filters means no restraint. This is exactly how Priya's "impossible" route reached FG-EDGE-DR.
Q2 — MODEL ANSWER
It matches the /24 itself (the base length is the implicit floor), and every /25 and /26 inside it. It does NOT match the /27 — that's longer than the le 26 ceiling. The window is /24 through /26 inclusive.
SECTION 01

Prefix Lists — the Floor and the Ceiling

The base prefix length is a floor; le raises the ceiling, ge raises the floor — and raising the floor evicts the base prefix itself.

images/s1-prefix-lists.png
Clean technical infographic on a cream background, deep navy and blue accents. A vertical ruler labeled "prefix length" from /24 at the bottom to /32 at the top. Three panels side by side: Panel 1 "198.51.100.0/24 (bare)" shows a single highlighted tick at /24 only. Panel 2 "/24 le 26" shows a shaded band covering /24, /25 and /26, with /24 marked "floor (included)" and /26 marked "ceiling". Panel 3 "/24 ge 26" shows a shaded band from /26 up to /32, with a red X on the /24 tick and a small caption "ge raises the floor — the base /24 no longer matches". Elegant serif labels, minimalist, no clutter.

A prefix-list is the route-map's matching tool for the prefix itself — the network address and its mask length. Each entry has three parts: the base prefix (e.g. 198.51.100.0/24), and two optional length modifiers, le (less-than-or-equal) and ge (greater-than-or-equal).

The mental model that makes every exam distractor readable: the base prefix length is the implicit floor, and the modifiers move the walls of a window. Written bare, the entry is an exact match — only the /24, nothing inside it, nothing broader. Add le 26 and the ceiling rises: now /24, every /25 inside it, and every /26 inside it all match, but a /27 is too specific and falls outside. Add ge 26 instead and the floor rises to /26 — which quietly evicts the base /24 itself, because /24 no longer satisfies "at least /26".

EntryMatched lengthsMatches the bare /24?
198.51.100.0/24/24 exactlyYes — and only it
198.51.100.0/24 le 26/24 – /26 (within the /24)Yes — base is the floor
198.51.100.0/24 ge 26/26 – /32 (within the /24)No — ge raised the floor past it
198.51.100.0/24 ge 25 le 27/25 – /27 (within the /24)No — floor is /25
Common misconception: "Adding ge just makes the match broader." It doesn't — ge can exclude the very prefix you wrote. If a question shows ge on an entry and asks whether the base prefix matches, the answer is no. This is the single most common prefix-list trap.
Exam tip: When you see le/ge in an answer set, don't reason in words — sketch the window. Floor = base length (or ge value if present). Ceiling = le value (or /32 if only ge, or the base if neither). Then check each candidate prefix against the window and the address range.
🧠
MENTAL NOTE
A prefix-list entry is a window on prefix length. Bare = exact. le raises the ceiling (base stays in). ge raises the floor (base gets pushed out).

💭 THINK FIRST · AS-PATH & COMMUNITIES

Priya wants a rule: "reject any route that passed through AS 65500 at any point in its path." Separately, Vaultline has 40 unsummarizable prefixes scattered across different subnets that all need Local Preference 150. Neither of these is a prefix problem.

  • Can a prefix-list express "reject anything that traversed AS 65500"? Why or why not?
  • What does tagging those 40 prefixes with one shared community label buy you that a 40-line prefix-list can't — think about when tagging happens versus when matching happens.
Q1 — MODEL ANSWER
No. A prefix-list only understands IP prefixes and mask lengths — it has no concept of the AS-PATH attribute at all. Different attribute, different tool: an AS-path access-list, which matches the AS-PATH string with a regex (e.g. _65500_ for "contains 65500 anywhere").
Q2 — MODEL ANSWER
Tagging happens ONCE, at origination — but the label travels with the route as an attribute, so matching on it can happen anywhere downstream, on any router, even in a different AS. Every downstream router needs just one rule ("if tagged X, do Y") instead of its own maintained copy of 40 prefixes. Add a 41st prefix? Tag it at the source; nothing downstream changes. Communities decouple policy from topology.
SECTION 02

Matching Beyond the Prefix — AS-Path ACLs & Communities

One route, three attributes, three matchers — each tool reads a different part of the same route.

images/s2-aspath-community.png
Clean technical infographic, cream background, navy/blue palette with one amber accent. Center: a stylized BGP route card labeled "198.51.100.0/24" with three visible attribute rows: "Prefix: 198.51.100.0/24", "AS-PATH: 65500 65210 65001", "Community: 65100:150". Three labeled magnifying glasses point at one row each: "prefix-list" at the prefix row, "as-path access-list (regex _65500_)" at the AS-PATH row, "community-list" at the community row. Small caption beneath: "same route — three different attributes — three different matchers". Elegant serif type, generous whitespace.

A route-map clause can match on more than the prefix — a BGP route carries multiple attributes, and each attribute has its own dedicated matcher. The AS-path access-list reaches into the AS-PATH string using a regex: "contains 65500 anywhere" is _65500_. Full BGP regex syntax is its own topic for a later session — for now, hold the concept: it lets policy see where a route has been, not just what it is.

The community-list matches on community tags — arbitrary labels attached to routes. Communities exist to solve a problem neither of the other tools can: policy for a set of routes that share no common prefix pattern and no common AS-PATH pattern. Instead of maintaining a 40-line prefix-list on every router in the path, you stamp all 40 routes with one label at origination and write a single downstream rule matching the label.

Analogy

Communities are luggage tags, not passenger lists.

  • A prefix-list is a passenger list at every gate — each gate agent needs their own copy, updated whenever a passenger changes.
  • A community is a priority tag attached to the suitcase at check-in — every handler downstream just reads the tag.
  • Add a new priority suitcase? Tag it at check-in. No gate agent's list changes. The tag travels with the bag.

Tag once at check-in; every handler downstream reads the same tag.

Remember: the deep reason communities exist — tagging happens once at origination, but the tag travels with the route, so matching can happen anywhere downstream. Communities decouple policy from topology.

MENTAL NOTE
Three matchers, three attributes: prefix-list → the prefix, AS-path ACL → where the route has been, community-list → the label someone chose to stamp on it.

💭 THINK FIRST · ROUTE-MAP ANATOMY

A route-map is a numbered sequence of permit/deny clauses; a route walks them top-down and stops at the first match. That "stops at first match" rule plus one hidden default explain nearly every route-map exam trap.

  • A route walks all six clauses of a route-map and matches none of them. What happens to it — and why would the designers choose that default?
  • A route matches a permit clause that carries a set local-preference 150. Is the route just admitted, or something more?
Q1 — MODEL ANSWER
Implicit deny — same instinct as firewall policy, same design logic: filtering tools must fail closed. If you forgot a clause, the safe failure is "route dropped," not "route silently admitted." A route-map's whole job is selective admission; an implicit permit would make it useless as a filter.
Q2 — MODEL ANSWER
Something more: matched-and-permitted means admit AND modify. The set statement fires, stamping the named attribute (here Local Preference 150) onto the route as it passes through. Match decides which routes a clause grabs; permit/deny decides whether they survive; set decides what changes on the way through.
SECTION 03

Route-Map Anatomy — Match, Verdict, Modify

Top-down, first match wins — and the floor beneath the last clause is always deny.

images/s3-route-map-anatomy.png
Clean vertical flow diagram, cream background, navy/blue with green and red accents. A route (small envelope icon labeled with a prefix) descends past numbered clause boxes: "10 · permit · match prefix-list A · set local-preference 150" (green edge), "20 · deny · match as-path ACL B" (red edge), "30 · permit (no match conditions — matches all)" (green edge). Arrows show the route stopping at the FIRST box it matches. Beneath the last clause, a solid dark bar labeled "IMPLICIT DENY — fail closed" with a small caption "a route-map of only deny clauses blocks everything". Elegant serif labels, minimal clutter.

The route-map is the machine the three matchers plug into: a numbered sequence of clauses, each one permit or deny, each optionally containing match conditions and (on permits) set actions. A route walks the clauses top-down and stops at the first clause it matches. The full picture in one line: match decides which routes a clause grabs, permit/deny decides whether they survive, set decides what changes on the way through.

Beneath the last clause sits an implicit deny — the same fail-closed philosophy as firewall policy. This creates the classic trap: a route-map containing only deny clauses blocks everything. The routes matching your denies get explicitly dropped, and everything else falls off the bottom into the implicit deny. To express "deny these, allow the rest," you need a final permit clause with no match conditions — an empty permit matches all.

And this closes a loop that has been open since Session 23: Local Preference "had nowhere to go" until iBGP existed — now you also know the mechanism that actually applies it: a route-map with set local-preference, applied inbound on a neighbor.

Common misconception: "My route-map denies the bad routes, so the good ones get through." Not unless you gave them a way through. Deny-only route-maps block everything — always look for (or add) the empty permit at the bottom.
Exam tip: When reading a route-map in a question, trace each candidate route top-down and stop at the first matching clause. Never keep evaluating past a match, and never forget the invisible deny below the final clause.
🧠
MENTAL NOTE
Match → verdict → modify. First match wins, implicit deny at the bottom, and "deny these / allow the rest" always needs an empty permit as the final clause.
