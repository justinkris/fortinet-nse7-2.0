SESSION 25 · NIBBLE · ROUTE MAPS

The Route-Map Machine

Three matchers plug into one machine: match decides, verdict admits or drops, set modifies.

BGP's default posture is trust and propagate everything. Route-maps are the only restraint.

Priya found ISP-A's peering route on FG-EDGE-DR — not a bug, just the unfiltered default doing exactly what it does. This page is the toolkit that stops it.

SECTION 01

Three Matchers, Three Attributes

images/nibble-25-three-matchers.png
One BGP route, three attributes, three dedicated matching tools.
Clean infographic, cream background, navy/blue palette. Center: a BGP route card showing three attribute rows — "Prefix: 198.51.100.0/24", "AS-PATH: 65500 65210", "Community: 65100:150". Three labeled arrows, one per row: "prefix-list → the prefix (le/ge window)", "as-path access-list → where the route has been (regex)", "community-list → the label stamped at origination". Elegant serif type, generous whitespace.

A BGP route carries multiple attributes, and each has its own matcher. The prefix-list matches the prefix itself, using the le/ge window: the base length is the implicit floor, le raises the ceiling (base stays in), ge raises the floor — evicting the base prefix. The AS-path access-list reaches into the AS-PATH via regex (_65500_ = traversed AS 65500 anywhere) — policy on where a route has been. The community-list matches arbitrary labels stamped on routes.

Communities solve what neither other tool can: policy for routes with no common prefix pattern and no common AS-PATH pattern. Tag once at origination; the label travels with the route, so matching happens anywhere downstream with one rule instead of a maintained prefix-list on every router. Communities decouple policy from topology.

SECTION 02

Match, Verdict, Modify

The route-map is a numbered sequence of permit/deny clauses. A route walks top-down and stops at the first clause it matches. Match decides which routes a clause grabs; permit/deny decides whether they survive; and on a matched permit, set fires — admit and modify, stamping Local Preference, MED, or a community onto the route on its way through. This is the mechanism that finally applies the Local Preference that "had nowhere to go" back in Session 23.

Beneath the last clause sits an implicit deny — the same fail-closed philosophy as firewall policy: if you forgot a clause, the safe failure is "dropped," never "silently admitted."

The trap: a route-map containing only deny clauses blocks everything — the denied routes explicitly, and all the rest via the implicit deny. "Deny these, allow the rest" always needs a final permit with no match conditions — an empty permit matches all.
Remember: first match wins. When tracing a route through a route-map, stop evaluating at the first matching clause — never carry on past it.
🧠
MENTAL NOTE
First match wins. Implicit deny at the bottom. Deny-only = block everything. The escape hatch is a trailing empty permit.
