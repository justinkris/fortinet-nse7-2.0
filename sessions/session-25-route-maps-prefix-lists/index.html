Concepts Learned

1BGP's unfiltered default: with no filters, a router accepts EVERYTHING an eBGP peer sends into its BGP table (full internet feed included) and re-advertises all of it onward — including into iBGP, since eBGP-learned routes are not blocked by iBGP split-horizon. "No filters means no restraint" — the leaked ISP-A route on FG-EDGE-DR wasn't a bug, it was the default working as designed. (Student initially jumped to BGP→IGP redistribution as the leak mechanism — right instinct, but the pure BGP-to-BGP propagation had to be isolated first.)
2Prefix-list le/ge window model: the base prefix length is the IMPLICIT FLOOR of a prefix-length window. Bare entry = exact match only. `le N` raises the ceiling (base stays included): /24 le 26 matches /24, /25s, /26s inside the range — NOT /27. `ge N` raises the FLOOR — which evicts the base prefix itself: /24 ge 26 matches /26–/32 within the range but NOT the bare /24. "Adding ge can exclude the very prefix you wrote" is the canonical exam trap.
3AS-path access-lists (concept only): a prefix-list has no concept of the AS-PATH attribute — different attribute, different matcher. AS-path ACLs match the AS-PATH string via regex (e.g. _65500_ = "traversed AS 65500 anywhere"). BGP regex syntax deliberately deferred to a dedicated future pass.
4Communities — policy decoupled from topology: community tags exist for route sets sharing NO common prefix pattern and NO common AS-PATH pattern (e.g. 40 scattered customer prefixes all needing LP 150). The key insight: tagging happens ONCE at origination, but the tag travels with the route as an attribute, so matching can happen anywhere downstream — every downstream router needs one rule ("if tagged X, do Y") instead of its own maintained 40-line prefix-list. Add a 41st prefix → tag at source, nothing downstream changes.
5Route-map anatomy: numbered sequence of permit/deny clauses; a route walks top-down and stops at the FIRST matching clause. Match decides which routes a clause grabs; permit/deny decides whether they survive; set decides what changes on the way through (matched-and-permitted = admit AND modify).
6Implicit deny + the deny-only trap: an unmatched route hits an implicit deny at the bottom — same fail-closed philosophy as firewall policy (safe failure = dropped, not silently admitted). Consequence: a route-map of ONLY deny clauses blocks EVERYTHING. "Deny these, allow the rest" requires a final permit clause with no match conditions (empty permit = matches all).
7Closing S23's loop: Local Preference "had nowhere to go" until iBGP existed (S24); the mechanism that actually APPLIES it is now known — a route-map with `set local-preference`, applied inbound on a neighbor.

Important Takeaways

  • BGP's default is trust-and-propagate-everything; every filter is an explicit act of restraint layered on top.
  • Prefix-list = a window on prefix length. Bare = exact. le raises the ceiling (base stays). ge raises the floor (base is EVICTED — the trap).
  • Three matchers, three attributes: prefix-list → the prefix; AS-path ACL → where the route has been; community-list → the label stamped on it. Communities' real value: tag once at origination, match anywhere downstream — policy decoupled from topology.
  • Route-map = match → verdict → modify. First match wins; implicit deny below the last clause; deny-only route-maps block everything; "deny these / allow rest" needs a trailing empty permit.
  • A matched permit with a set statement admits AND modifies — this is the mechanism that applies Local Preference, MED, and community stamps.
