Weakness Session 01 · FGCP Internals

The Peer Review That Almost Shipped Wrong

Six claims from another team's FGCP design doc. All six read plausibly. All six were wrong in the same specific ways you were, once.

💭 THINK FIRST · HEARTBEAT ID

A design doc claimed FGCP heartbeats ride VLAN-tagged frames (0x8100) and fail over in ~600ms. Both numbers look reasonable. Both are wrong — and wrong for related reasons: borrowing conventions from adjacent technologies instead of asking what a heartbeat actually needs.

  • What is 0x8100 actually for, and does a heartbeat between two directly-adjacent HA peers need that job done?
  • If the real detection window were only 3 missed heartbeats (~600ms), what would that do to a cluster sitting behind a switch doing STP recalculation?
Q1 — MODEL ANSWER
0x8100 signals "an 802.1Q VLAN tag follows" — a switch's tool for keeping multiple logical networks apart on a shared trunk. A heartbeat link is typically a direct, single-purpose L2 segment between two known peers; there's no ambiguity to resolve, so there's nothing for a VLAN tag to do. What the frame actually needs is a way to say "I am FGCP hello traffic" — that's FGCP's own registered EtherType, 0x8890, unrelated to 0x8100 despite the superficial resemblance as hex strings.
Q2 — MODEL ANSWER
600ms of tolerance would make the cluster hair-trigger — a momentary CPU spike or a switch's STP recalculation could eat 2-3 heartbeat cycles without the peer being remotely unhealthy, causing a false failover (and its full cost: vMAC reassignment, GARP, NP7 resync) for no real reason. That's why the actual default is far more conservative: hb-lost-threshold = 20 at 200ms intervals, ≈4 seconds — roughly 6-7x more forgiving than the "3 missed beats" instinct borrowed from other protocols' dead-timers.
CORRECTION 01 + 02

0x8100 Is a Different Job

The trap here is purely visual: 0x8100 and 0x8890 are both four-digit hex EtherTypes, and it's easy for the eye to blur them together under exam pressure. But they do completely unrelated jobs. 0x8100 belongs to 802.1Q — it tells a switch "a VLAN tag follows, use it to keep this frame in the right broadcast domain." 0x8890 is FGCP's own registered EtherType for hello/heartbeat frames — it tells the receiving NIC "this is FGCP hello traffic, interpret it accordingly." One is about switch-level traffic segregation; the other is about protocol self-identification. They happen to share a numbering neighborhood and nothing else.

The threshold trap runs on the same logic in a different direction: "3" is a plausible-sounding default because it's common elsewhere (OSPF/HSRP-style dead timers), but FGCP's actual default is hb-lost-threshold = 20 at the standard 200ms interval, giving roughly a 4-second detection window. The gap between the guessed 600ms and the real ~4s isn't a rounding error — it's the difference between a cluster that flaps on every transient blip and one that tolerates real-world noise.

💭 THINK FIRST · LINK DISCIPLINE

The doc claimed two heartbeat links (hbdev priorities p3=10, p4=20) would load-balance "like session-sync-dev." That comparison is backwards — and the reason why says something important about what heartbeat and session-sync are each trying to guarantee.

  • With p3=10 and p4=20, which link is preferred, and what does the other one do while the first is healthy?
  • Why would you NOT want two heartbeat links simultaneously and independently reporting peer-alive status?
Q1 — MODEL ANSWER
Lower priority number wins (same convention as OSPF cost, admin distance). p3 (priority 10) is the active heartbeat link, carrying 100% of heartbeat traffic. p4 (priority 20) sits completely idle for heartbeat purposes — pure standby — until p3 fails, at which point FGCP fails over to it.
Q2 — MODEL ANSWER
You want one authoritative source of truth for "is my peer alive," with a clean deterministic fallback — not two links that could theoretically disagree or introduce timing skew in reporting peer status. Session-sync-dev has the opposite requirement: it's bulk data mirroring (the session table), where spreading traffic across multiple links for more bandwidth is a straightforward win with no downside.
CORRECTION 03

Ordered/Exclusive, Not Load-Balanced

Heartbeat links with configured priorities (hbdev "p3" 10 "p4" 20) behave as an ordered, exclusive list: the lowest-numbered priority is active and carries all heartbeat traffic; every other configured heartbeat interface sits idle as pure standby, promoted only on failure of the active link. There is no simultaneous sharing of heartbeat traffic across links, ever.

The doc's comparison to session-sync-dev inverts the actual pairing. Session-sync-dev is the one that genuinely load-balances — when multiple session-sync links are configured, FGCP spreads the session-table mirroring traffic across all of them, because that job (bulk data replication) benefits straightforwardly from more available bandwidth. Heartbeat and session-sync have opposite disciplines because they solve opposite problems: one needs a single authoritative, low-latency signal; the other needs throughput for a large, continuously-changing dataset.

Exam tip: This pairing (heartbeat = ordered/exclusive, session-sync = load-balanced) is a classic distractor. If a question describes load-balancing behavior and asks which interface type it applies to, the answer is almost always session-sync-dev, not hbdev.
🧠
MENTAL NOTE
Heartbeat links: ordered/exclusive, lower priority number wins, backup is pure standby. Session-sync links: load-balanced across all configured interfaces. Two different jobs, two opposite disciplines.

💭 THINK FIRST · OVERRIDE SEMANTICS

Priya's question in the doc: "override is off, so Box B keeps primary permanently after Box A comes back, right?" This is the single most counter-intuitive mechanic in the whole cluster — the correct answer depends entirely on how long the outage was.

  • If Box A reboots and rejoins within 90 seconds, does Box B have a decisive uptime lead over it yet? What does the waterfall fall through to if not?
  • Why does a SHORT outage let a higher-priority box preempt, while a LONG outage locks the survivor in — backwards from most people's first guess?
Q1 — MODEL ANSWER
No — Box B's uptime lead needs to reach 5 minutes to be decisive. At 90 seconds, the uptime comparison is a tie by the rules (no clear winner), so the election waterfall falls through to the next criterion: priority. Whichever box has the higher configured priority wins — which could be Box A, despite override being off.
Q2 — MODEL ANSWER
A short outage (<5 min) never lets Box B's uptime lead become decisive, so the waterfall falls through past uptime to priority — meaning a higher-priority Box A can still reclaim primary despite override off. A long outage (≥5 min) lets Box B's uptime lead become decisive on its own, so the waterfall stops at the uptime criterion and priority is never even checked — Box B keeps primary regardless of its priority value. "Override off" only removes priority from being checked FIRST; it doesn't remove priority from the waterfall entirely.
CORRECTION 04

Override Off Is Not "No Preemption, Ever"

The most common misreading of override-off is that it disables preemption entirely — that once a peer takes over as primary, it stays primary no matter what. That's wrong, and the failure mode is specifically about outage duration relative to the 5-minute uptime margin.

The election is a waterfall: monitored interfaces → HA uptime (decisive only with a ≥5-minute lead) → priority → serial number, stopping at the first criterion that produces a clear winner. A short outage never lets the survivor's uptime lead cross the 5-minute threshold, so the comparison is a tie and the waterfall falls through to priority — where a higher-priority box, even the one that just rebooted, can still reclaim primary. A long outage lets the survivor bank a decisive uptime lead on its own, so the waterfall stops there and priority is never consulted at all.

Common misconception: "Override off = no preemption" is a genuine intuition trap because it's true in the long-outage case and false in the short-outage case. The correct model is "override off removes priority from being checked first" — not "override off removes priority from the equation."
🧠
MENTAL NOTE
Short outage → uptime tie → falls through to priority → higher-priority box can reclaim primary. Long outage → uptime lead decisive → priority never checked → survivor keeps primary. Backwards from first instinct — that's exactly why it's tested.

💭 THINK FIRST · A-A MECHANICS

Two more claims from the doc: the load-balancing hash uses IP Identification for "granular per-packet distribution," and Box B relays its replies back through Box A because Box A owns the vMAC. Both claims sound mechanically plausible. Both fail the same kind of test once you ask what the mechanism actually has to guarantee.

  • If the hash input changes on every packet, can two packets from the same session even land on the same box? What does that imply about valid hash inputs?
  • Does Box B need to "own" the vMAC to send a reply — or does the vMAC only matter for the client's incoming ARP resolution?
Q1 — MODEL ANSWER
No — if the hash input varies packet-to-packet (like IP Identification), consecutive packets in the same session could hash to different outcomes, splitting a single session's state across two boxes. That's disqualifying. The only field guaranteed stable for the life of a session is the 4-tuple (source/dest IP, source/dest port), so that's the real hash input, computed once at the SYN and never recalculated mid-session.
Q2 — MODEL ANSWER
The vMAC only matters for the client's outbound packets reaching the cluster — the client ARPs for the cluster IP, gets the vMAC, and its frames land on Box A (the vMAC owner). Box B doesn't need to own or spoof the vMAC to reply; TCP/IP doesn't require a reply to originate from the same MAC the original request targeted. Box B simply sends its reply using its own physical MAC. Door IN is always Box A; door OUT is always Box B — for the whole session, not just the first packet.
CORRECTION 05 + 06

Stable Inputs, Asymmetric Paths

The hash-input error and the return-path error share a root cause: both import an assumption from how a naive, simpler system might work, rather than asking what the actual constraint is. For the hash input, the constraint is "every packet in a session must resolve to the same box" — which immediately disqualifies anything that varies per packet, like IP Identification, and points to the 4-tuple as the only valid input. The decision is made once, at the SYN, and never revisited mid-session.

For the return path, the naive assumption is that the box owning the vMAC (Box A) must relay every reply back through itself, since that's the MAC the client resolved. But the vMAC's job ends once the packet reaches the cluster — it doesn't gate outbound traffic. For proxy-inspected A-A sessions, Box B replies to the client directly using its own physical MAC. This produces a genuinely asymmetric path for the life of the session: every inbound packet transits Box A (which relays it to Box B over the FGCP forwarding EtherType, 0x8891), and every outbound packet is sent by Box B with no involvement from Box A at all.

DirectionBoxMechanism
Inbound (client/server → cluster)Box AReceived on vMAC, relayed to Box B via 0x8891
Outbound (cluster → client/server)Box BSent directly, own physical MAC, no relay through A
Exam tip: This asymmetry directly explains a real troubleshooting trap — a packet capture taken only on Box A for a proxy-inspected A-A session can show a SYN with no visible SYN/ACK, looking like a failed handshake, when the session actually completed fine on Box B. Rule: always check both boxes before declaring an A-A session broken.
🧠
MENTAL NOTE
Hash input = 4-tuple, decided once at the SYN — never a per-packet-varying field. Door IN is always Box A, door OUT is always Box B, for the whole session — this is the single highest-value fact in the A-A cluster.
