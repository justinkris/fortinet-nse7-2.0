FortiOS CLI Command Taxonomy

Understanding why the CLI is structured the way it is — so you can reason your way to the right command even when you've never seen it before.

The CLI isn't a list of commands to memorise. It's a taxonomy you can reason through.
If you understand why each root command exists, you can predict where an unknown command lives — and that's what separates senior engineers from command-memorisers.

SECTION 01

The Five Root Commands — A Mental Model

FortiOS splits its CLI into distinct root-level commands, each with a fundamentally different purpose. This isn't arbitrary — it reflects a deliberate design philosophy: what you're doing determines which root command you're under. Understanding the taxonomy means you can navigate the CLI by reasoning, not by memory.

The cleanest first dividing line is between commands that change state and commands that observe state. Only one root command writes to the configuration. Only one performs irreversible actions. The rest are observational — but they observe very different things.

config
Writes Config
The only command that modifies the FortiGate configuration database. Requires elevated privileges. All configuration changes happen here — policies, interfaces, routing, VPNs. Changes persist across reboots.
show
Reads Config
Displays only what has been explicitly configured — settings that differ from factory defaults. Silent on anything that hasn't been touched. Use show full-configuration to see everything including defaults.
get
Reads State
Retrieves real-time operational state — routing tables, ARP cache, interface status, current sessions. Think of it as asking "what is the firewall doing right now?" Clean, summarised output prepared for administrators.
execute
Performs Action
Triggers an immediate action — ping, traceroute, reboot, failover, backup. Does not modify stored configuration but can have irreversible real-world consequences. Always think before running execute on production.
diagnose
Deep Internals
Exposes raw internal engine state and runs active diagnostic tests. Goes far deeper than get. Packet capture, debug flow, session table internals, process CPU usage — anything that requires reaching inside a running engine.
🧠
Mental Model
config = write · show = read config · get = read state · execute = do something · diagnose = look inside
The show trap: If a setting is at its default value, show will not display it. Engineers troubleshooting default-value bugs often miss the culprit entirely because they trusted show. Always use show full-configuration when you suspect a default setting is the problem.
Execute warning: execute reboot, execute factoryreset, and execute ha failover are immediate and often service-impacting. There is no confirmation prompt on some versions. Always verify you're on the correct device before running execute commands.
SECTION 02

The Read Commands — get vs show vs diagnose

Three commands all appear to "read" information from the firewall — but they read fundamentally different things. Choosing the wrong one gives you incomplete or misleading information.

Command What it reads Example use case Output style
show Stored configuration — explicit changes only Review a firewall policy, check interface config Clean, hierarchical config format
show full-configuration Stored configuration — including all defaults Find a default setting that may be causing issues Complete config dump — very verbose
get Real-time operational state Check routing table, ARP cache, interface UP/DOWN Summarised, readable operational output
diagnose Raw engine internals + active test results Packet capture, debug flow, session flags, process CPU Raw, verbose, engine-level detail

The key insight is that get and diagnose both read real-time data — but at very different depths. get gives you a clean summary the system has already prepared. diagnose reaches inside the running engine and pulls out raw internals, or actively generates new data through testing.

💡 Analogy
Think of a car dashboard. get is the dashboard — it shows you speed, fuel level, engine temperature. Prepared, clean, at-a-glance. diagnose is a mechanic plugging in an OBD-II scanner and pulling raw fault codes from the engine control unit. Far more detail, but you need to know what you're looking at. show is the owner's manual — it describes how the car was configured at the factory and what the owner changed.
🧠
Mental Model
get = dashboard · diagnose = OBD-II scanner · show = owner's manual · show full-configuration = factory specification sheet

SECTION 03

The diagnose Command — Deep Dive

The diagnose command tree is where serious troubleshooting happens. It exposes raw engine state that has no clean GUI equivalent, and it runs active tests that generate new diagnostic information in real time. There are two commands every FortiGate engineer must know cold: packet sniffer and debug flow.

diagnose sniffer packet — Packet Capture

Sniffer Syntax
diagnose sniffer packet <interface> '<filter>' <verbosity> <count> <timestamp>

# Examples:
diagnose sniffer packet port1 'host 192.168.1.10 and port 80' 4 100
diagnose sniffer packet any 'host 192.168.1.10' 4 0
diagnose sniffer packet wan1 'icmp' 6 50
VerbosityWhat you see
1IP header only — source IP, dest IP, ports, protocol
2Level 1 + interface direction (in/out)
3Level 2 + ethernet frame (MAC addresses)
4Level 3 + hex payload — most useful for general troubleshooting
6Level 4 + ASCII payload — readable application data
Pro tip — use 'any' for asymmetric routing detection: Capturing on any shows traffic on all interfaces simultaneously. You can confirm which interface traffic actually egresses on (may not be what you expect), and verify NAT translation by seeing the pre-NAT source on ingress and the post-NAT source on egress — all in a single capture.

diagnose debug flow — Internal Decision Tracing

Debug flow is the most powerful troubleshooting tool in FortiOS. It shows you exactly what FortiGate does with a specific packet — which policy it matched, whether NAT applied, whether it was dropped and why. Use it when the sniffer shows packets arriving but not leaving.

Debug Flow Sequence — Always Follow This Order
# Step 1: Set filter (what traffic to trace)
diagnose debug flow filter addr 192.168.1.10
diagnose debug flow filter daddr 8.8.8.8          # optional: destination filter
diagnose debug flow filter proto 6                  # optional: protocol (6=TCP, 17=UDP, 1=ICMP)

# Step 2: Configure output
diagnose debug flow show console enable
diagnose debug flow show function-name enable       # optional: shows internal function names

# Step 3: Enable debug and start trace
diagnose debug enable
diagnose debug flow trace start 100                 # 100 = packet count to trace

# Step 4: Reproduce the issue (ping, browse, etc.)

# Step 5: ALWAYS clean up when done
diagnose debug flow trace stop
diagnose debug disable
Critical: Always run diagnose debug disable when finished. Debug output consumes CPU and memory. On a busy production firewall this can compound an already degraded situation. Senior engineers treat this like closing a gas valve — you never leave without checking it's closed.

🧠
The Sniffer vs Debug Flow Rule
Sniffer = what arrives at the wire. Debug flow = what FortiGate decides to do with it. If sniffer shows packets arriving but not leaving → use debug flow to find out why.
SECTION 04

The Troubleshooting Toolkit

These are the commands that come up again and again in real-world FortiGate troubleshooting. Knowing these cold — not just what they do, but when to reach for them — is what separates confident engineers from those who guess.

Connectivity & Routing

CommandWhen to use it
get system arpStart here — confirms Layer 2 is working and gateway MAC is known
get router info routing-table allIs the route even in the table? Check before anything else
get router info routing-table details <ip>Confirm which route wins the longest prefix match for a specific destination
execute ping-options source <ip>Set source IP before pinging — always set this to test the correct path
execute ping <ip>Test basic reachability from FortiGate itself
execute traceroute <ip>Map the actual path packets take — find where they stop
execute ping-options df-bit yesSet DF bit — used for MTU/PMTUD troubleshooting
execute ping-options data-size <bytes>Set packet size — find MTU ceiling by incrementing until failure
The ping trap: A successful ping from FortiGate confirms routing and connectivity for traffic originating on the firewall. It tells you almost nothing about whether user traffic through FortiGate is permitted. User traffic hits security policies, NAT, and UTM inspection. FortiGate's own traffic bypasses all of that.

SECTION 05

The Golden Troubleshooting Sequence

When a user can't reach something, experienced engineers follow a logical sequence — from the outside in, from the simple to the complex. This prevents thrashing around and ensures you don't skip a layer that would have revealed the problem immediately.

Step 1
get system arp
Layer 2 working? Gateway MAC known?
→
Step 2
get system interface
Is the interface UP? Correct IP?
→
Step 3
get router info routing-table all
Is the route present?
→
Step 4
execute ping-options + execute ping
Can FortiGate reach it? (Set source first!)
Step 5
diagnose sniffer packet any
Is user traffic actually arriving?
→
Step 6
diagnose debug flow
What is FortiGate doing with it?
→
Step 7
diagnose sys session list
Is a session being created? Any offload flags?
→
Step 8
diagnose debug disable
Always. Every time. Without exception.
🧠
The Three Rules
1 — Always disable debug when done. 2 — show silence on a setting means it's at default; use show full-configuration. 3 — A successful ping from FortiGate tells you nothing about user traffic through FortiGate.
SECTION 06

Conceptual Self-Test

💭 Self-Test Questions
  • A junior engineer says "I checked the config with show and the MTU looks fine." Why might this be a misleading statement, and what command should they have used instead?
  • You run a ping from FortiGate to 8.8.8.8 and it succeeds. Users on the 192.168.1.0/24 subnet still can't browse the internet. What does the successful ping tell you — and what does it NOT tell you?
  • You suspect a session helper is preventing NP offload. Which command reveals the session flags that would confirm this — and why does it live under diagnose rather than get?
  • You need to run a packet capture but only want to see TCP traffic on port 443 from a specific host. Write the complete sniffer command.
  • A colleague leaves for lunch mid-troubleshooting with debug enabled. What is the risk — and which two commands fix it?
Model answers summary: (1) show only displays explicit changes — default MTU would be silent. Use show full-configuration. (2) The ping confirms routing and connectivity for FortiGate's own traffic — but user traffic through FortiGate hits security policies, NAT, and UTM. These are entirely separate paths. (3) diagnose sys session list — it lives under diagnose because it exposes raw internal engine flags, not a clean operational summary. (4) diagnose sniffer packet any 'host 192.168.1.10 and port 443' 4 100 (5) Debug consumes CPU/memory and can degrade production. Fix: diagnose debug flow trace stop then diagnose debug disable.
